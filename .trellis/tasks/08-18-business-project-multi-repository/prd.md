# 业务项目多仓库知识模型

## Goal

将 NEXUS 的“业务项目”和“GitLab 代码仓库”拆成两个明确层级，使一个业务项目可以拥有
一套共享需求、版本与 Wiki，并关联多个独立同步和索引的代码仓库。以 Immortal 为首个迁移
对象，避免把 `immortal-api`、`immortal-game-service` 等仓库误建成彼此无关的项目。

同时修复已发布代码索引在项目摘要中显示为 0 的统计错误，保证项目级汇总与仓库级状态均
反映真实 Qdrant live alias 数据。

## Background

- Immortal 的需求文档描述整个业务项目，不属于某一个代码仓库。
- 一个 Immortal 业务项目由多个 GitLab 仓库共同实现；每个仓库有独立分支、commit、Webhook、
  同步状态和代码索引。
- 当前 `RagProperties.ProjectConfig` 同时持有一个需求 collection、一个代码 collection 和
  一个 repository path，实际表达的是一对一“项目即仓库”模型。
- GitLab 账号导入按每个远端仓库自动生成独立 `projectId`，连接项目又设置 `knowledge=null`，
  因此仓库项目的需求、版本和 Wiki 统计均为 0。
- `ProjectRegistry.group` 只能按字符串查找同组项目，不是持久化的业务项目/仓库归属关系，
  Wiki、权限、统计和主要检索路由仍以仓库级 `projectId` 为边界。
- `bizgame-immortal-api` 已成功发布 1263 个代码 point 到
  `bizgame_immortal_api_code-live`；`ProjectController`、`RuntimeStatusController` 和
  `KnowledgeManagementController` 却对基础名 `bizgame_immortal_api_code` 计数，该 collection
  不存在，所以页面错误显示代码为 0。
- Immortal 的版本主仓库固定为 `immortal-game-service`。当前本地 `master` 根 `pom.xml` 版本为
  `5.2.0`，提交历史包含合并 `V5.2.0`；现有需求快照最高为 `5.1`，因此当前产品版本应来自
  主仓库，需求状态应显示落后。
- 当前工作区已有 `immortal-game-service` 的需求、代码与 Wiki 数据，需要设计兼容迁移，避免
  重做已有向量和 Wiki 资产。

## Requirements

- 引入稳定的业务项目实体。业务项目拥有名称、共享需求知识、复合版本基线、Wiki 和访问控制
  边界。
- 引入稳定的仓库实体。仓库属于且只属于一个业务项目，拥有 GitLab 远端身份、分支、代码
  collection/live alias、本地仓库路径、同步任务、Webhook 与索引 commit。
- 普通业务仓库不得同时归属多个业务项目。跨项目复用的代码必须建模为独立“公共库”，而不是
  把同一个 GitLab 仓库重复导入或重复归属。
- 公共库拥有独立 GitLab 身份、同步、版本和索引生命周期；业务项目通过引用关系使用公共库，
  不复制其仓库记录、Webhook、任务历史或 Qdrant 索引。
- 公共库不会自动进入全部业务项目。每个业务项目显式维护所引用的公共库集合；未引用公共库
  不参与该项目的默认检索、开发方案或 Wiki 证据生成。
- 管理界面为业务项目仓库和公共库提供独立入口。业务项目详情展示自有仓库及“已引用公共库”，
  但公共库不混入自有仓库列表或被显示为业务项目所有。
- 权限只配置在业务项目级。仓库、需求、Wiki、版本基线和联合检索全部继承业务项目访问权限，
  本任务不引入仓库级独立 ACL。
- GitLab 导入必须选择已经在项目管理中创建完成的目标业务项目；导入向导不允许现场创建业务
  项目，也不得再把远端仓库自动当成新业务项目。
- 业务项目创建流程负责设置稳定 ID、名称、版本主仓库策略、需求来源和访问控制；配置不完整的
  业务项目不可用于 GitLab 导入。
- GitLab 批量导入在批次级统一选择一个目标业务项目。批次内每个仓库仍可分别配置分支、
  端类型和代码 collection，但不得分别选择或隐式创建其他业务项目。
- 同一业务项目可关联多个 GitLab 连接、多个仓库和不同端类型，仓库同步失败不得覆盖业务项目
  的共享需求或其他仓库索引。
- 项目级检索默认使用一套共享需求，并联合检索该业务项目下所有已启用且索引可用的仓库；
  API/UI 应允许在需要时缩小到单个或部分仓库。
- 版本主仓库只决定业务项目产品版本，不限制代码检索范围。默认代码范围包含业务项目下全部
  已启用且索引可用的仓库；停用、未索引或无权限仓库不进入默认候选集。
- 代码命中必须携带仓库标识、仓库名称、commit 和文件路径，避免多仓库出现同名文件或符号时
  无法辨识来源。
- 产品版本以代码库声明的业务版本为唯一来源，不由需求文档版本决定。commit 用于精确追溯，
  但产品主版本展示代码库的完整版本标识。
- 每个业务项目必须指定且只能指定一个版本主仓库。Immortal 的版本主仓库为
  `immortal-game-service`；其他仓库不得覆盖项目产品版本。
- Immortal 业务项目的稳定 ID 为 `immortal`。`immortal-game-service` 和
  `bizgame-immortal-api` 是其仓库 ID，不再作为彼此独立的业务项目 ID。
- 现有以 `immortal-game-service` 为项目 ID 的 URL、需求快照和 Wiki 资产必须通过迁移映射或
  兼容别名归入 `immortal`，旧入口不得直接失效。
- 主仓库版本应从受支持的构建元数据中解析。Immortal 当前以 Maven 根 `pom.xml` 的项目版本
  `5.2.0` 为真实来源，同时保留解析来源路径、原始版本和对应 commit 供审计。
- 产品 UI 保留完整三段版本并加 `v` 前缀，例如原始 Maven 版本 `5.2.0` 展示为 `v5.2.0`；
  不折叠为 `v5.2`。
- 公共库版本不参与业务项目产品版本计算。业务项目版本基线仍记录每个已引用公共库的版本与
  commit；公共库变化可触发依赖变化和 Wiki 过期提示，但不得把 Immortal 产品版本改掉。
- 需求版本用于表示文档覆盖到哪个产品版本。需求版本低于代码产品版本时，系统必须明确展示
  版本缺口，例如“产品 v5.2.0，需求 5.1，缺少 v5.2.0 需求”，不得把产品版本降为 5.1，
  也不得因需求滞后把代码索引判定为失败。
- 产品版本高于最新需求版本时，检索、开发方案和 Wiki 可继续使用最后一个可用需求版本，但
  每条需求证据及整体结果必须同时标记需求证据版本、目标产品版本和“需求落后”状态；历史
  需求不得被解释为当前产品版本的完整需求。
- Wiki 与版本知识归属业务项目；代码证据必须可记录多个仓库各自的 commit，需求证据必须记录
  需求仓库版本，而不是只有一个项目级 `codeCommit` 或 `requirementVersion`。
- 业务项目摘要展示共享需求数量、关联仓库数量、聚合代码分块数和 Wiki 版本数；仓库详情展示
  自身代码分块数、同步状态、分支、commit、Webhook 和任务历史。
- 所有代码统计统一读取检索实际使用的 live alias；不存在、不可用和真实 0 必须可区分，不得
  把统计异常静默伪装成成功的 0。
- 现有静态单仓库项目和现有 API 应有明确兼容策略；迁移不得删除或重新嵌入已经可复用的 Qdrant
  collection、alias、需求快照或 Wiki 文件。
- Immortal 迁移后，现有 `immortal-game-service` 知识资产与 `bizgame-immortal-api` 代码索引
  应归入同一业务项目，并保留各仓库原始 GitLab 身份和同步历史。
- 现有资产迁移不得在应用启动时自动执行。管理员先获得迁移预览，再显式确认一次性幂等迁移；
  失败时可回滚或安全重试，未迁移前旧入口继续可用。

## Acceptance Criteria

- [ ] 项目列表只把 Immortal 展示为一个业务项目，并展示真实的共享需求、聚合代码和 Wiki 数量。
- [ ] 新业务项目 ID 为 `immortal`；旧 `immortal-game-service` 项目入口可跳转或解析到
      `immortal`，同时仓库详情仍使用 `immortal-game-service` 仓库身份。
- [ ] Immortal 当前版本从主仓库根 `pom.xml` 自动识别并展示为 `v5.2.0`，页面不再
      显示“未设置版本”，并同时显示需求最高版本为 `5.1`、需求落后。
- [ ] Immortal 详情可列出至少 `immortal-game-service` 和 `bizgame-immortal-api` 两个仓库，
      每个仓库保留独立状态、分支、commit 和同步操作。
- [ ] `bizgame-immortal-api` 仓库详情和 Immortal 聚合摘要均能读取 live alias 中的 1263 个
      point，不再显示错误的 0。
- [ ] 从 GitLab 导入新仓库时必须明确选择归属业务项目，导入完成后不产生新的孤立业务项目。
- [ ] GitLab 导入向导只列出可用的既有业务项目，不包含“快速创建项目”；没有可用业务项目时
      引导用户返回项目管理入口创建。
- [ ] 一次批量导入只能归属一个业务项目；提交前页面持续展示目标业务项目，仓库级配置不包含
      第二个业务项目选择器。
- [ ] 面向 Immortal 的联合检索只读取一次共享需求，并可返回多个仓库的代码命中；每条代码命中
      可明确辨识仓库和 commit。
- [ ] 未指定仓库筛选时，Immortal 代码检索覆盖全部可用仓库；指定一个或多个仓库后，结果严格
      收敛到所选范围，且主仓库身份不改变该规则。
- [ ] 同一普通 GitLab 仓库不能关联到两个业务项目；公共库只索引一次，并可被多个业务项目
      引用且明确标记为公共来源。
- [ ] Immortal 可显式添加或移除公共库引用；添加后默认检索包含该公共库，移除后不再召回，
      且不会删除公共库本身或影响其他业务项目。
- [ ] 管理界面可分别浏览项目仓库和公共库；同一个公共库在多个项目中只显示为引用，不重复
      出现同步任务、Webhook 或索引记录。
- [ ] 在产品 `v5.2.0`、需求最高 `5.1` 的情况下，检索仍能使用 5.1 证据，但响应和 UI 明确
      显示“需求 5.1 落后于产品 v5.2.0”，且不声称需求覆盖完整。
- [ ] 单个仓库停用或同步失败时，Immortal 的需求、Wiki 和其他仓库索引仍可用，项目摘要显示
      部分降级而不是整体清零。
- [ ] 用户有 Immortal 访问权时可访问其全部仓库知识；无 Immortal 访问权时，不能通过仓库 ID
      绕过业务项目权限读取代码、同步状态或源码。
- [ ] Wiki 以代码库业务版本作为产品版本，并记录多仓库 commit 基线；需求版本落后时，Wiki
      明确标记缺失需求证据及受影响页面，而不是生成虚假的同版本需求。
- [ ] 公共库升级后，Immortal 产品版本仍由主仓库保持不变；版本基线和过期检查能指出具体
      公共库的版本/commit 变化。
- [ ] 现有索引和 Wiki 资产完成原地迁移或兼容挂接，无需重新调用嵌入模型才能恢复可用状态。
- [ ] 迁移预览列出业务项目、主仓库、普通仓库、需求快照、Wiki、Qdrant alias 和任务历史的
      源/目标映射；未确认时不产生持久化变更。
- [ ] 同一迁移重复执行不会复制仓库、公共库引用、任务历史或向量数据；中途失败可继续重试。
- [ ] 新增覆盖项目/仓库关系、导入归属、聚合统计、多仓库检索、Wiki 多 commit 和迁移回滚的
      后端与浏览器回归测试。

## Constraints

- API 嵌入模型保持现有 OpenAI 兼容配置，不引入或切换到 Ollama。
- PAT 和 Webhook Secret 的加密、Host 绑定与一次性展示边界保持不变。
- 现有 GitLab 项目级串行队列仍以仓库为粒度，不能改成整个业务项目串行。
- 本任务是复杂跨层变更，开始实现前必须补齐 `design.md` 与 `implement.md`。
