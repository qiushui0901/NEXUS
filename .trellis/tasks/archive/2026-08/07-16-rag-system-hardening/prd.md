# RAG 系统短板治理

## Goal

在不破坏现有需求导入、需求评审、开发方案、代码检索和 SSE 接口的前提下，系统性解决当前 RAG 的检索链路不一致、代码解析脆弱、错误被伪装为空命中、引用不可追溯以及大文档上下文截断问题，使质量能够量化、失败能够诊断、答案能够回查。

## Background

- 需求评审链已经具备查询改写、Dense/Sparse 混合召回、BGE 重排和 LLM 重排；开发方案的需求检索只执行混合召回后截断，链路不一致。
- 文档采用 2000 字符父块、500 字符子块和 80 字符重叠；检索子块但向生成层提供父块。
- 稀疏检索使用中英文词项的 Java `hashCode` 映射，并由 Qdrant IDF modifier 调整权重。
- Java 代码索引主要依赖正则表达式和括号范围识别类、方法及粗粒度类型关系。
- 多个查询、路由和重排调用捕获运行时异常后返回空列表、原始排序或默认项目，调用方难以区分“无结果”和“依赖故障”。
- 开发方案只在响应末尾附带文档摘录和代码命中，生成结论与证据之间没有稳定的逐项引用契约。
- 需求评审会读取版本全文并拼接上下文，超长文档最终依赖字符截断，可能丢失后部模块。
- 内置 `monitor.html` 前端会把非 2xx HTTP 视为失败；SSE 已识别 `retrieval`、`references`、`completed` 和 `error` 事件，因此可以通过新增事件与可选字段保持向后兼容。
- 当前工作区包含大量未提交修改，本任务必须保留并兼容这些既有改动。

## Requirements

### R0：质量基线

- 从现有产品文档、历史存疑和代码仓库整理约 50 条真实查询，覆盖中文业务别名、精确配置词、跨模块问题、无答案问题和代码符号定位；候选结果必须经过人工抽查确认。
- 建立可重复运行的离线评测集，记录期望文档块、代码符号和应无答案标记。
- 评测集以脱敏 JSONL 存放在 `src/test/resources/rag/eval/`，只提交查询、稳定证据 ID、类别和 `no_answer` 标记，不复制产品原文、源码片段或完整上下文。
- 至少统计 Recall@K、MRR/nDCG、重排前后变化、无答案准确率、端到端延迟和外部模型调用次数。
- 后续每个子任务必须通过相同评测集证明没有不可接受的回退。

### R1：统一检索与重排

- 把查询改写、混合召回、父块恢复、重排、截断和诊断信息抽象成可配置管线。
- 需求评审和开发方案复用同一需求检索管线，仅通过 profile 决定 TopK、重排层级和上下文预算。
- 保留代码检索的描述向量、源码向量、稀疏向量和关键词召回能力，并统一重排结果与诊断契约。
- 查询改写或重排失败时允许明确降级，但必须记录降级原因。

### R2：可靠的 Java 代码解析

- 使用 Java AST/符号解析替代正则作为主要符号来源。
- 采用 JavaParser + Symbol Solver；项目当前没有 AST 依赖，Java 版本为 21。
- 正确处理类、接口、枚举、record、构造器、重载、嵌套类型、注解、继承与实现关系。
- 保持现有 `CodeChunk` 及 Qdrant payload 的兼容读取能力；索引版本变化必须可识别、可重建。
- 采用影子解析与新 collection 迁移：先并行对比旧正则和 AST 结果，再写入版本化代码 collection，验证通过后切换配置并保留旧 collection 作为回滚点。

### R3：错误与降级治理

- 明确区分成功有结果、成功无结果、部分降级和请求失败。
- 外部依赖故障不得默认伪装成“没有命中”；API/SSE 应提供稳定、可机器识别的错误或 warning 契约。
- 为路由、查询改写、Embedding、Qdrant、BGE、LLM 重排和生成分别记录阶段、原因、耗时及降级路径。
- 保留允许的弹性降级，避免单个非关键重排器故障导致整条请求不可用。
- 可降级故障继续返回可用结果，并附加 `DEGRADED` 状态、阶段 warning；SSE 使用新增的 `warning` 事件。
- 核心依赖故障且没有可用结果时，HTTP 返回明确的 502/503；SSE 发送 `error` 事件后结束。
- 真正的零命中保持成功响应，并标记为 `NO_RESULTS`，不得与依赖故障混淆。

### R4：证据级引用

- 每条关键结论、开发环节或存疑问题能够引用一个或多个稳定证据 ID。
- 采用结构化条目级引用：产品规则、开发环节、风险和存疑问题返回 `evidenceIds`；SSE 的 `section` 事件携带同一字段。
- 文档证据至少包含 collection/project、documentId、version、filename、parentId 和摘录定位。
- 代码证据至少包含 projectId、commitSha、filePath、symbol、行号范围和 chunk ID。
- 服务端验证模型返回的证据 ID，只允许引用本次检索上下文中的证据。
- 前端将证据 ID 渲染为可点击标签，末尾继续发送完整 `references` 列表；首期不要求模型在自然语言中插入 `[1]`、`[2]` 编号。
- 同步和 SSE 响应使用同一引用数据模型。

### R5：大文档分段处理

- 超出单次上下文预算的文档按模块或父块批次执行 Map 阶段，再由 Reduce 阶段合并、去重和排序。
- 分组采用路径模块优先、固定父块批次兜底：优先使用版本目录或模块目录；没有明确模块时按 `parentOrder` 分批。
- 不再通过简单尾部截断决定哪些模块进入评审。
- 处理过程具备批次上限、超时、部分失败和重试策略，并能报告覆盖了哪些文档模块。
- 小文档继续走低成本快速路径。

### R6：兼容与安全

- 保持现有 REST 路径、权限校验和默认请求字段兼容；新增字段优先采用向后兼容方式。
- 不删除或覆盖用户现有未提交修改。
- 索引格式升级必须提供明确的重建方式和回滚说明。

## Acceptance Criteria

- [ ] 固定评测集能够在本地一条命令运行，并输出可比较的 JSON/报告。
- [ ] 开发方案与需求评审通过统一需求检索接口工作，profile 差异有自动化测试覆盖。
- [ ] 同一评测集上，新的默认管线相对基线没有 Recall@10 回退，并记录延迟与调用成本变化。
- [ ] AST 索引测试覆盖 record、重载、嵌套类型、注解、继承和实现关系，不再依赖正则作为主要解析结果。
- [ ] 模拟 Qdrant、Embedding、BGE、路由 LLM 和生成 LLM 故障时，响应能够区分失败与真正的零命中。
- [ ] 同步开发方案、SSE 开发方案和存疑结果中的引用均能被服务端解析并回查到本次检索证据。
- [ ] 超过单次上下文预算的大文档能够覆盖全部批次；单批失败不会无提示地丢失模块。
- [ ] 现有接口契约测试、权限测试、索引测试和端到端测试通过。
- [ ] 每个子任务都提供独立回滚点，父任务完成前执行一次全链路回归。
- [ ] 新管线相对旧管线的 Recall@10、MRR/nDCG 回退不超过 5%；`no_answer` 查询不出现明显的虚构命中增长。
- [ ] 端到端延迟或外部模型调用次数增加超过 30% 时，评测报告明确列出原因和取舍。

## Delivery Structure

采用分阶段交付，每个阶段独立评测、上线和回滚：

1. 第一阶段：`07-16-unify-retrieval-rerank` 与 `07-16-rag-error-degradation`，先建立质量基线、统一检索/重排并修复错误契约。
2. 第二阶段：`07-16-evidence-citations`，建立证据模型与同步/SSE 引用。
3. 第三阶段：`07-16-ast-code-indexing`，切换 AST 代码索引并执行索引迁移。
4. 第四阶段：`07-16-large-document-map-reduce`，引入大文档 Map-Reduce 处理。

父任务负责公共验收、接口兼容和最终集成，各子任务独立规划、实现和验证。

## Notes

- 这是复杂父任务，进入实现前必须具备 `design.md` 和 `implement.md`，并分别完成子任务规划。
