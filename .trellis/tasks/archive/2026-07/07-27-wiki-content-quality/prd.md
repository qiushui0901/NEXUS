# Wiki 内容质量基线

## Goal

把 目标版本 Wiki 从“Git 文件和提交摘要集合”改造成可阅读、可核验、可追溯的版本知识：每个需求功能都能看到需求事实、业务规则、处理流程、代码入口、测试状态、风险和证据来源。

## Requirements

- 以本地需求版本快照作为需求事实来源，但不得提交快照文件本身，也不得把向量、Qdrant 数据、凭据或本地路径写入 Wiki。
- 一个需求条目生成一个稳定功能页；文件名、版本和内容哈希共同形成可追溯身份，不得把名称相近的不同需求自动合并。
- 页面必须区分“需求原文事实”“静态代码证据”“测试建议”“真实测试执行结果”；没有真实测试快照时明确显示“没有真实执行快照”。
- 页面至少支持：功能说明、需求来源、业务规则、处理流程、代码入口、数据/配置影响、异常与边界、测试与验收、版本变化、证据列表。
- 自动生成的业务规则和流程只能来自需求文本中的标题、编号、列表或明确句子；无法可靠解析时保留原文摘录并标记待审核，不得编造。
- 代码证据必须来自指定 Git commit 的真实文件和符号；无法关联代码时明确显示“尚未关联代码实现”，不得用文件数量代替功能实现。
- 目标版本正式 Wiki 中不再生成按仓库模块罗列的空洞页面；版本概览只承担导航和覆盖率说明。
- 现有 schemaVersion=1 页面继续可读；新版页面使用向后兼容的可选字段。
- Wiki 浏览页优先按业务知识结构展示，并对所有 API 文本做 HTML 转义。

## Acceptance Criteria

- [x] 目标版本的每个有效需求条目都有独立 Wiki 功能页，标题和摘要来自需求证据，而不是 Git 提交说明。
- [x] 每个功能页至少包含一条需求证据；代码、测试缺失时有清晰状态，不伪造结论。
- [x] 页面能展示业务规则、流程步骤、数据/配置影响、边界条件、代码入口和测试/验收建议。
- [x] 5.1 页面列表不再包含自动生成的“模块文件清单”页面，版本概览显示需求覆盖率、代码关联率和真实测试快照状态。
- [x] 旧 Wiki JSON 仍能被后端反序列化并在浏览器中显示。
- [x] 生成器和浏览页面有回归测试；Java 21 全量测试、Python 生成器测试和 Git 差异检查通过。

## Constraints

- 保持原生 HTML/CSS/JavaScript，不引入前端构建系统。
- 本阶段只建立 5.1 高质量基线和通用生成能力，不承诺一次性重建全部历史版本。
- 不提交 `data/requirement-snapshots/**`、`.env`、Qdrant storage、向量、本地索引或凭据。
