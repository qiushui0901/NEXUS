# 重建第二阶段版本 Wiki 实质内容

## 背景
当前版本中心依赖版本档案，而历史版本 Wiki 大多只有“版本概览”占位页，不能回答产品、开发、测试对某个版本到底改了什么。第二阶段采用第二种方案：以版本代码边界和真实仓库内容为主线自动构造可审阅 Wiki 草稿，再发布到对应版本目录；没有需求或测试证据时必须显式标注缺失，不能编造。

## 目标
- 为每个已登记版本生成至少一份有实质内容的版本知识页，内容来自对应 Git commit 的文件统计、变更文件和 Java 类型/方法结构。
- 对有基线的版本生成“版本变更概览”页，明确新增、修改、删除文件、Java/测试/配置数量。
- 保留已有人工 Wiki 源定义的产品事实和边界，不覆盖已有页面；自动内容作为补充证据。
- 提供可重复执行的本地构建命令，直接从 Git 快照补齐正式 Wiki 源和渲染结果；需要需求事实审核时继续使用现有 `data/wiki-drafts` 流程。
- 继续禁止向量、Qdrant 运行数据、本地凭据进入 Wiki 源或生成物。

## 非目标
- 本阶段不让 LLM 直接编造产品规则。
- 不把完整源码复制进 Wiki；只保存路径、类型/方法名和受控短摘录。
- 不提交向量库、索引、WAL 或 `.codebase-memory`。

## 验收标准
1. 对一个有 Git commit 的版本执行构建，草稿包含版本概览、代码变更概览和按模块归纳的代码证据，不能再只有占位文案。
2. 对有 `baseCodeCommit` 的版本，草稿明确列出 diff 统计；无基线时明确标注“无基线，仅展示版本快照”。
3. 自动生成内容带 `CODE`/`GIT` 证据，测试区在没有真实执行快照时显示“没有真实执行快照”。
4. 同一输入重复构建结果稳定（除 buildId/generatedAt 外），路径安全，旧 Wiki 不被破坏。
5. 单元测试覆盖无仓库、非法 commit、文件过滤、内容脱敏和草稿生成。
6. Java 21 下 `./mvnw -B verify` 通过，`git diff --check` 通过。
