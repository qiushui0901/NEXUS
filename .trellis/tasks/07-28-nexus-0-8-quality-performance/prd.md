# NEXUS 0.8：检索质量与性能

## Goal

将 0.7 已打通的统一检索入口升级为可度量、可回归、可降级的质量与性能基线，使需求评审、开发计划和 Wiki 构建三种 profile 都使用同一套并行召回、重排和缓存策略。

## Requirements

### R1 — 统一重排

- 需求证据在 `RetrievalPipeline` 内按可配置策略执行 BGE 重排，并支持可选 LLM 精排。
- `DEVELOPMENT_PLAN`、`REQUIREMENT_REVIEW`、`WIKI_BUILD` 三种 profile 均经过统一重排阶段。
- `DoubtReviewService` 不再在管线外重复执行 BGE/LLM 重排。
- 重排依赖失败时保留原始混合检索顺序，并返回结构化 warning，不得拖垮其余召回结果。

### R2 — 并行召回与隔离降级

- 需求混合检索、版本语料滚动读取、代码检索按 profile 并发执行。
- 每个召回分支有独立、可配置的超时；单分支失败或超时只降级该分支。
- 结果状态应区分成功、无结果、部分降级和整体失败，并保留阶段 warning。

### R3 — 有界缓存

- embedding 缓存：按模型指纹和规范化文本缓存向量，支持 TTL 与最大条目数。
- 检索结果缓存：键至少包含 query、project、document、version、profile、limit、语料选项与检索配置指纹；只缓存稳定结果。
- Wiki 页面与版本索引缓存：按 project/version/feature 缓存，并在对应版本发布后失效。
- 缓存不得跨项目、跨版本污染；所有缓存均可通过配置关闭。

### R4 — 评测数据与质量门禁

- 版本化评测集不少于 50 条。
- 覆盖正常召回、版本泄漏、相似功能误召回、空结果、依赖降级、跨项目污染。
- 产出 Recall@10、MRR 和 P95 延迟报告。
- CI 对评测集契约、数据量和确定性离线回归执行强制门禁；真实依赖评测保留显式开关。
- CI 增加 JaCoCo 最低覆盖率与依赖漏洞扫描。

### R5 — MCP 0.8 能力

- 新增第十个工具 `nexus_conflict_check`，复用现有确定性冲突检测服务与 MCP 权限/审计边界。
- 提供三个 MCP Prompt：`实现某需求`、`评审某需求`、`评估改动影响`，指导客户端组合已有工具且保持项目/版本作用域。
- MCP 服务版本升级为 `0.8.0`。

### R6 — 兼容性与可观测性

- 保持现有 REST 与 MCP 工具输入输出兼容。
- 为并行分支、重排和缓存命中/未命中提供可观测事件或指标。
- 默认配置在没有 BGE、LLM、Qdrant 等外部依赖时仍可通过单元测试和应用上下文测试。

## Non-goals

- 不在 0.8 引入 Redis 或其他新的共享基础设施；缓存为进程内有界缓存。
- query rewrite / multi-query 属于可选增强，本次不作为发布阻塞项。
- 不改变 0.7 的权限模型、项目注册表或 Wiki 文件格式。

## Acceptance Criteria

- [ ] 三种 retrieval profile 都由统一管线完成需求证据重排，评审服务无重复重排。
- [ ] 需求、语料和代码召回可并行执行，分支超时/异常会独立降级。
- [ ] embedding、检索结果和 Wiki 页面缓存均有 TTL、容量边界及隔离/失效测试。
- [ ] 评测集不少于 50 条并覆盖六类指定场景。
- [ ] CI 的 Recall@10/MRR 回归、JaCoCo 覆盖率和依赖漏洞检查可阻断失败构建。
- [ ] 受控基准证明开发计划检索 P95 相对顺序执行基线下降至少 30%。
- [ ] 新增 `nexus_conflict_check` 与三个 MCP Prompt，并有契约测试。
- [ ] `./mvnw verify` 通过，0.8 冒烟测试通过。
