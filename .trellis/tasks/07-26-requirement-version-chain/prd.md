# 需求版本链补齐

## Goal

让版本中心能够从业务版本追溯到对应的需求文档版本，并在没有本地向量库数据时仍能展示真实、可审阅的需求差异。

## Requirements

- 业务版本必须能够解析到明确的 `requirementDocumentId` 与 `requirementVersion`，不得只保留一个无来源的版本标签。
- 优先使用人工保存的正式版本档案；未保存正式档案时，可根据 Wiki 版本和受控需求快照合成只读版本档案。
- 从现有历史需求表和当前版本产品文档生成轻量需求快照，快照只包含来源、文本、顺序和内容哈希，不包含 embedding、向量库 point、Qdrant storage、snapshot 或凭据。
- 需求差异优先读取受控需求快照；快照不存在时兼容现有 Qdrant 版本数据。
- 至少补齐 `5.0.2 -> 5.1` 的需求链路，并覆盖现有需求材料能明确映射的历史业务版本。
- 没有可靠需求材料的版本必须继续显示“未绑定/不可用”，不得推断为“没有变化”。
- 版本中心继续展示新增、修改、删除及变更前后摘要。
- 提供可重复执行的生成工具，后续新增需求版本时不需要手工编辑大量 JSON。

## Constraints

- 不提交向量库数据、本地索引、IDE 数据、凭据或 2.8GB 的原始 ZIP。
- 不覆盖人工维护的正式版本档案。
- 保持现有 API 与原生 HTML/JavaScript 页面兼容。
- 历史小版本只有在需求材料明确属于同一需求基线时才允许映射到同一需求版本。

## Acceptance Criteria

- [x] `/api/versions/manifests?projectId=immortal-game-service` 能为 5.0.2 和 5.1 返回需求文档绑定。
- [x] 比较 5.0.2 与 5.1 时，`requirements.availability` 为 `AVAILABLE`，页面可展示真实需求条目摘要。
- [x] 需求比较不依赖仓库中的 Qdrant/向量数据。
- [x] 受控快照记录来源文件、来源位置、内容哈希和生成时间。
- [x] 现有正式版本档案优先级高于自动合成档案。
- [x] 无材料版本保持明确 warning，不伪造需求差异。
- [x] 新增单元/接口契约测试并通过完整 Maven 验证。
