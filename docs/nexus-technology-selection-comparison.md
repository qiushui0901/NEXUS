# NEXUS 技术选型与代表产品对比

> 目标：从代码上下文平台、企业知识搜索、编码执行 Agent 三个方向，分析代表产品如何构建 AI 上下文，并说明我们准备建设的研发证据平台及其预期优势。
>
> 说明：产品能力来自公开资料。厂商未公开的内部模型、索引和排序细节，不作为确定事实。

## 1. 核心判断

研发 AI 市场主要有三个方向：

| 方向 | 代表产品 | 优先解决的问题 |
|---|---|---|
| 代码上下文平台 | Sourcegraph | 如何在大型代码库中准确找到代码、符号和关系 |
| 企业知识搜索 | Atlassian Rovo | 如何连接文档、工单、人员和项目知识 |
| 编码执行 Agent | GitHub Copilot、Qoder | 如何理解任务、修改代码、运行测试并交付结果 |

三类产品各自很强，但研发过程还缺少一层稳定的内部事实：

- 需求属于哪个业务版本；
- 需求对应哪些代码和符号；
- 哪些测试结果支持当前版本；
- Wiki 是临时生成内容还是经过审核的正式知识；
- Agent 使用了哪些来源；
- 信息不足、版本不一致或证据冲突时如何处理。

我们准备建设的不是第四种通用 AI 产品，而是连接三类产品的研发证据层：

```text
Sourcegraph 类代码上下文    Rovo 类企业知识    Copilot / Qoder 类 Agent
            \                 |                 /
             \                |                /
              ------ 研发证据平台 ------
            需求版本、代码、测试、Wiki、证据关系
```

## 2. 三个选型方向

### 2.1 代码上下文平台：Sourcegraph

#### 产品定位

Sourcegraph 的核心价值是让开发者和 AI 在大型、多仓代码库中快速找到准确上下文。Cody 在代码搜索基础上提供问答、生成和修改能力。

#### 公开的技术组成

Sourcegraph 官方资料明确列出 Cody 的三类上下文来源：

1. **Keyword Search**：使用关键词和自动查询改写寻找代码；
2. **Sourcegraph Search API**：利用 Sourcegraph 自身的代码搜索基础设施检索本地和远程仓库；
3. **Code Graph**：利用代码元素之间的结构关系寻找相关上下文。

整体方式可以概括为：

```text
GitHub / GitLab / Bitbucket 等代码仓库
  -> 持续代码索引
  -> 文件、符号、定义、引用和关系
  -> 关键词搜索 + 结构搜索 + Code Graph
  -> 根据用户问题选择相关上下文
  -> 注入 Cody Chat、生成或修改任务
```

Sourcegraph 并不是简单地把源码切块后只做向量搜索。它以成熟代码搜索为基础，再将符号和代码图信号用于上下文获取。这使它在精确类名、方法名、引用位置和跨仓使用关系上优于纯语义 RAG。

#### 技术优势

**大规模索引**

代码索引和检索是 Sourcegraph 的核心产品，而不是附属能力。它适合大量仓库、长周期增量更新和多团队共享。

**关键词与结构信号并存**

精确标识符适合关键词或符号搜索，架构关系适合 Code Graph，业务语言可以通过查询改写或模型理解补充。多信号比单一 embedding 更稳定。

**跨仓上下文**

Cody 可以使用多个远程仓库作为上下文，适合基础库、服务端、客户端和 SDK 分散在不同仓库的场景。

**IDE 与搜索产品一体化**

搜索结果可以直接进入 Cody，开发者不需要在独立知识系统和 IDE 之间反复切换。

#### 相对目标场景的不足

Sourcegraph 的核心对象仍然是代码：仓库、文件、符号、引用和代码关系。它并不以业务需求版本为中心，因此需要其他系统补充：

- 需求版本的冻结和差异；
- 需求与代码实现之间的正式关系；
- 测试执行快照；
- Wiki 审核与发布状态；
- 需求、代码、测试和 Wiki 的联合比较；
- 产品存疑和跨来源冲突。

它可以帮助 Agent 找到“相关代码”，但不能单独保证 Agent 使用的是与目标业务版本匹配的需求、代码和测试证据。

#### 我们准备怎么做

我们不准备复制完整 Sourcegraph，而是建设面向研发证据的代码上下文能力：

1. **混合代码检索**：组合精确关键词、语义向量和代码业务描述，避免只依赖 embedding；
2. **编译器级语义索引**：逐步接入 Java、TypeScript、Go 的 LSP 或编译器索引，获得定义、引用、类型和接口实现关系；
3. **显式工程关系**：补充 HTTP Route、RPC、消息 Topic、配置绑定和数据库对象关系，覆盖普通调用图看不到的跨服务链路；
4. **commit 级快照**：所有代码关系绑定 Git commit，避免用当前代码解释历史需求；
5. **证据化输出**：代码结果返回仓库、commit、文件、符号、行号和解析置信度；
6. **影响分析**：从需求、符号或 commit diff 出发，给出受影响入口、调用者和建议回归范围。

#### 预期优势

我们的目标不是在通用代码搜索规模上超过 Sourcegraph，而是在业务版本追溯上形成优势：

```text
Sourcegraph：问题 -> 相关代码上下文

我们的规划：需求版本 -> 代码证据 -> 调用影响 -> 测试范围 -> 可回查来源
```

这样得到的不只是代码搜索结果，而是可以进入需求评审、版本比较和测试决策的证据。

### 2.2 企业知识搜索：Atlassian Rovo

#### 产品定位

Rovo 的目标是让 AI 理解企业中的人员、项目、工作项和知识。它以 Atlassian 体系为中心，同时通过 connector 接入第三方 SaaS。

#### 公开的技术组成

Rovo 官方重点强调两部分：

1. **Connectors**：连接 Jira、Confluence、GitHub、GitLab、Google Drive、Teams、Figma 等系统；
2. **Teamwork Graph**：连接团队、工作、目标和项目上下文。

整体方式可以概括为：

```text
Jira / Confluence / GitHub / Drive / Teams / 其他 SaaS
  -> Connector 抽取对象和内容
  -> 保留来源、组织关系和访问边界
  -> Teamwork Graph 连接人员、工作和目标
  -> Search / Chat / Agent / Workflow
```

Rovo 的优势不是某一种向量算法，而是它已经位于企业工作流中：需求在 Jira，文档在 Confluence，团队关系和工作状态也在 Atlassian 平台。

#### 技术优势

**连接器广度**

企业不需要先把所有数据迁移到一个新系统。Rovo 可以从现有 SaaS 拉取上下文。

**组织关系与工作关系**

通过 Teamwork Graph，搜索结果不只是文本相似，还可以结合项目、人员、目标和工作项关系。

**数据产生和消费在同一工作流**

用户可以在 Jira、Confluence、桌面、浏览器和命令行中使用 Rovo，搜索结果还能进入 Agent 和自动化流程。

**适用范围广**

它不只服务开发，还能服务产品、运营、销售、支持和管理团队。

#### 相对目标场景的不足

Rovo 以企业对象和 connector 为中心，通常不会深入维护以下代码和版本语义：

- 某个 Git commit 下的符号图；
- 方法重载、接口实现和调用关系置信度；
- 需求父块和检索子块；
- test case 级真实执行快照；
- 代码索引版本及发布完整性；
- 需求、代码、测试和 Wiki 的统一证据 ID。

它可以搜索到 Jira 需求和 GitHub 仓库，但“这个需求版本具体由哪些代码实现，哪些测试证明它有效”仍需要专用研发模型。

#### 我们准备怎么做

我们不准备建设全公司通用搜索，而是聚焦研发知识：

1. **建立统一研发对象模型**：项目、需求版本、代码 commit、符号、测试 case、Wiki feature；
2. **接入少量高价值来源**：需求平台、Git 仓库、CI 测试报告、版本 Wiki；
3. **保留原始来源与快照**：每条知识都能回到具体文档、工单、commit 或测试报告；
4. **建立跨来源关系**：需求关联代码入口，代码影响关联测试，Wiki 汇总已审核事实；
5. **版本化而非只索引当前状态**：支持比较两个业务版本，而不是只搜索最新文档；
6. **与企业平台集成而非替代**：未来通过 connector 或 API 读取 Jira、Confluence 等来源，不重新建设工单和协作系统。

对于底层数据 Serving，我们准备保持可替换：中小规模使用专用向量数据库和轻量元数据存储；如果未来需要与公司实时数仓进行大规模 SQL 和向量联合查询，再评估 Hologres 等平台。

#### 预期优势

```text
Rovo：连接更多企业系统，让用户找到组织知识

我们的规划：连接关键研发系统，让 Agent 获得同一版本下的一组可验证事实
```

优势来自研发深度，而不是 connector 数量：

- 能比较历史需求版本；
- 能区分当前代码和历史 commit；
- 能判断测试快照是否缺失；
- 能把 Wiki 限定为审核后的正式知识；
- 能发现需求、代码、测试和 Wiki 之间的冲突。

### 2.3 编码执行 Agent：GitHub Copilot 与 Qoder

这一方向选择两个代表：GitHub Copilot 代表代码托管和 IDE 生态驱动的 Agent；Qoder 代表 Repo Wiki、持久上下文和长任务 Agent 路线。

#### GitHub Copilot 怎么做

GitHub Copilot 已覆盖 IDE、CLI、GitHub Web、代码评审和云端 Agent。其公开 MCP 方案允许 Copilot 调用外部系统提供的工具和数据。

可以概括为：

```text
当前文件 / 工作区 / GitHub Issue / PR / Repository
+ GitHub 原生工具
+ 外部 MCP Server
  -> Copilot Agent
  -> 编辑代码、运行任务、评审或创建 PR
```

它的核心优势是执行闭环：代码、Issue、PR、Review 和 CI 都在 GitHub 生态中，Agent 可以从理解任务直接走到交付。

#### Qoder 怎么做

Qoder 官方强调三类能力：

- **Enhanced Context Engineering**：组合代码、知识、规则、工具和环境形成持久上下文；
- **Repo Wiki**：预先分析代码库，生成架构和设计知识；
- **Goal-Oriented Loop**：围绕目标执行、验证和迭代，支持长时间任务与多 Agent 协作。

可以概括为：

```text
代码库
  -> 预分析和 Repo Wiki
  -> 规则、记忆、工具和当前任务上下文
  -> 多 Agent 规划与长任务执行
  -> 修改、验证、迭代直到交付
```

Repo Wiki 的价值是把高频探索提前完成。Agent 不必每次重新扫描整个仓库，而是先阅读已经压缩的架构、模块和设计知识，再按需读取源码。

#### 两类 Agent 的技术优势

**执行能力成熟**

它们可以编辑文件、调用终端、运行测试并处理 PR，远超单纯问答系统。

**当前任务上下文丰富**

编辑器光标、打开文件、用户选择、Issue、PR 和历史交互都可以进入上下文。

**预编译上下文降低探索成本**

Qoder Repo Wiki、DeepWiki 和各类 repository context files 能减少 Agent 的重复搜索和 token 消耗。

**扩展生态成熟**

Copilot 使用 MCP 接入外部工具，Qoder 使用 Skills、Plugins、Rules 和工具扩展能力。

#### 相对目标场景的不足

Agent 的核心目标是完成当前任务，而不是维护长期版本事实。它读取的 Wiki、Issue 和搜索结果可能来自不同时间点，也可能是模型生成摘要。

仅依靠 Agent 自身上下文，难以稳定保证：

- 使用的是正确业务版本；
- Repo Wiki 与目标 commit 一致；
- 需求和代码证据没有跨项目污染；
- 测试结论来自真实 CI 快照；
- 引用能够长期回查；
- 信息不足时不会继续生成看似完整的实现方案。

预编译 Wiki 也存在过期风险。如果没有 commit、来源哈希和发布状态，Wiki 可能降低探索成本，同时传播旧结论。

#### 我们准备怎么做

我们不准备自建编码 Agent，而是成为 Agent 的可信上下文服务：

1. **通过 MCP 暴露研发工具**：需求检索、代码检索、源码、调用图、影响分析、版本差异、Wiki、存疑和冲突；
2. **返回解析后的范围**：服务端明确告诉 Agent 最终使用了哪个项目、需求版本和 commit；
3. **建设版本化 Context**：预生成需求和代码 Wiki，但每个页面绑定版本、来源哈希和审核状态；
4. **支持按需下钻**：Agent 先读取架构和功能摘要，再通过证据 ID 获取源码或需求原文；
5. **限制上下文预算**：根据任务选择需求、代码、图关系或 Wiki，不把全部内容塞入 prompt；
6. **建立质量反馈**：记录哪些证据被使用、哪些结论缺少支持，并用固定评测集验证上下文质量；
7. **保持 Agent 可替换**：Copilot、Qoder、Cursor、Claude Code 或未来 Agent 共用同一证据协议。

#### 预期优势

```text
Copilot / Qoder：把当前任务执行完成

我们的规划：确保不同 Agent 执行任务时，使用同一套正确版本和可回查证据
```

这会带来三个优势：

1. **避免客户端锁定**：更换 Agent 不需要重新建设内部知识；
2. **避免上下文漂移**：Repo Wiki、需求、代码和测试都绑定明确版本；
3. **执行与事实解耦**：Agent 可以快速迭代，内部事实和证据契约保持稳定。

#### 国内产品全景

国内 AI 编码产品已经覆盖 IDE 插件、独立 IDE、Agent、企业知识库、Repo Wiki、测试生成和云端任务等多种形态。选型时可以广泛了解，但不应把所有产品都当成同一类能力。

| 产品 | 厂商或背景 | 公开能力重点 | 适合重点考察 |
|---|---|---|---|
| 通义灵码 | 阿里云 | IDE/独立 IDE、工程自动感知、Agent、终端执行、多文件编辑、测试 Agent、企业知识库 | 企业规范增强、阿里云生态、研发任务闭环 |
| Qoder | 阿里系团队 | Context Engineering、Repo Wiki、Rules/Memory、Skills/Plugins、多 Agent、长任务执行 | Repo Wiki、持久上下文、长任务 Agent |
| CodeBuddy | 腾讯云 | AI 编码助手、工程理解、代码生成与研发协作 | 腾讯云和腾讯研发工具生态 |
| 文心快码 Comate | 百度 | 代码补全、问答、生成、测试和企业研发场景 | 百度云生态、企业编码辅助 |
| MarsCode | 字节跳动相关产品路线 | 云端开发、代码理解、生成和 Agent | 云 IDE、工程上下文、开发环境集成 |
| TRAE | 字节跳动 | AI IDE、Builder/Agent、多文件修改、工具和 MCP | AI IDE、Agent 执行和 MCP 生态 |
| CodeArts Snap | 华为云 | 代码生成、解释、测试及 CodeArts 研发流程集成 | 华为云、DevOps 全流程协同 |
| Fitten Code | 非十大厂团队 | 补全、问答、生成、测试等开发辅助 | 轻量 IDE 助手和个人开发体验 |
| 豆包 MarsCode / 火山引擎相关研发助手 | 字节生态 | 模型、云开发和研发工具结合 | 字节云和模型生态集成 |

这张表用于建立国内市场覆盖，不代表产品能力等价，也不代表所有能力都已公开稳定提供。

在国内产品中，建议优先深入研究四个代表：

**通义灵码：企业知识与工程感知**

通义灵码官方公开能力包括工程自动感知、文件编辑、终端执行、研发问答和测试 Agent。企业知识库可以上传代码规范文档，用于辅助代码优化和补全。

值得借鉴：

- 规范文档直接进入编码过程；
- Agent 自动感知工程框架、代码文件和错误信息；
- 测试生成后继续编译、运行和修复；
- 企业知识与 IDE 入口结合，用户不需要切换系统。

需要进一步验证：企业知识的版本管理、引用粒度、索引更新、召回解释和跨项目隔离能力。公开页面没有披露完整底层实现，不能直接断言其使用何种向量库或 Code Graph。

**Qoder：Repo Wiki 与持久 Context Engineering**

Qoder 明确强调 Repo Wiki、Memory and Rules、Comprehensive Context、多 Agent 和长任务执行。它的重点不是单次问答，而是预先理解代码库并保存可复用上下文。

值得借鉴：

- 先生成 Wiki，再让 Agent 按需深入源码；
- 把规则、知识、工具和环境都视为 Context；
- 长任务中持续保留目标和上下文；
- Wiki 作为人和 Agent 共用的代码库入口。

需要重点关注：Wiki 如何增量更新、如何与 commit 绑定、摘要错误如何纠正，以及生成 Wiki 的成本。

**CodeBuddy：腾讯研发与云生态入口**

CodeBuddy 的价值更可能体现在腾讯云、代码托管、IDE 和团队研发流程的一体化。对于已使用腾讯云研发工具链的团队，生态集成可能比单一模型能力更重要。

评估时应重点验证：

- 是否支持企业私有知识和代码规范；
- 工程级上下文范围；
- 多仓库理解；
- Agent 能调用哪些终端和研发工具；
- 是否提供代码图、影响分析或可回查引用；
- 私有部署和数据边界。

**文心快码 Comate：企业编码辅助**

Comate 可作为国内成熟企业编码助手代表。评估重点不应只看补全率，还应关注：

- 企业代码和规范如何进入上下文；
- 是否支持工程级、多文件任务；
- 测试和代码评审能力；
- 与百度云和企业研发平台的结合；
- 知识更新和引用可解释性。

由于其公开页面未在本次检索中提供足够技术细节，内部实现应以正式产品文档、PoC 和厂商技术交流为准。

#### Wiki / Context 提效专项

Wiki 提效不是简单“自动生成文档”，而是减少 Agent 和开发者重复探索代码库的成本。

典型产品和形态包括：

| 产品或形态 | 核心做法 | 主要收益 |
|---|---|---|
| Qoder Repo Wiki | 预先分析仓库，生成架构和设计知识 | Agent 长任务少走重复搜索路径 |
| DeepWiki | 将代码仓库生成可浏览、可问答的 Wiki 和系统图 | 快速理解陌生仓库、辅助 onboarding |
| Google 类 Code Wiki | 将代码结构和摘要组织成可浏览知识 | 统一代码理解入口 |
| `AGENTS.md` / `CLAUDE.md` / Rules | 人工维护仓库约定、命令和边界 | 低成本向 Agent 注入部落知识 |
| Repository Map | 预计算文件、符号、依赖和摘要 | 用较少 token 提供全局代码地图 |
| 架构决策与运行手册 | 人工审核的 ADR、故障处理和开发规范 | 保存无法从源码直接推断的知识 |

Wiki/Context 的主要提效来自四个方面：

1. **减少探索调用**：Agent 不需要每次重新扫描目录、构建文件和入口；
2. **减少 token**：先读取压缩摘要，再按需下钻源码；
3. **统一人机认知**：开发者和 Agent 使用同一份模块、流程和约定；
4. **保存部落知识**：记录为什么这样设计，而不仅是代码现在长什么样。

但 Wiki 也有明显风险：

- 代码变化后 Wiki 过期；
- 模型生成的错误摘要被长期传播；
- 全量重建大仓库成本高；
- Wiki 只描述结构，未必包含业务版本和真实测试状态；
- 多份 Context 文件可能互相冲突。

我们准备建设的 Wiki/Context 体系应吸收这些产品的提效方式，同时增加版本和证据治理：

1. **分层 Context**：仓库级架构、模块级说明、功能级 Wiki、符号级证据；
2. **绑定 commit 和来源哈希**：让 Agent 知道 Context 对应哪版代码；
3. **增量失效**：代码或需求变化时，只标记相关页面过期并重建；
4. **人机分工**：模型生成草稿，人审核后才成为正式 Context；
5. **按需下钻**：Wiki 只提供导航和摘要，事实仍通过证据 ID 回到源码、需求和测试；
6. **冲突检测**：Context 与当前代码、需求版本或测试状态不一致时显式告警；
7. **多 Agent 共用**：通过 MCP Resource 或标准文件格式同时服务 Copilot、Qoder、Claude Code、Cursor 等客户端。

预期优势不是生成更多文档，而是形成“可失效、可审核、可追溯”的 Context：

```text
普通 Repo Wiki：代码 -> 摘要 -> Agent 阅读

我们的规划：需求版本 + commit + 测试
             -> Wiki 草稿
             -> 来源与一致性校验
             -> 人工审核发布
             -> Agent 按证据下钻
```

## 3. 我们准备建设的总体方案

围绕三个方向，我们准备建设以下平台：

```text
需求与企业文档              Git 仓库与编译器索引              CI 测试结果
       |                            |                            |
       -------- 统一项目、版本、commit 和证据模型 --------
                                  |
              语义检索 + 代码关系 + 版本化 Wiki
                                  |
                证据校验、冲突检测、影响分析
                                  |
                       MCP / REST / SSE
                                  |
             Copilot / Qoder / Cursor / 其他 Agent
```

### 3.1 规划重点

**版本统一**

需求版本、Git commit、测试快照和 Wiki 版本必须能够互相解析，避免不同时间点的数据被拼成一个答案。

**代码关系升级**

从通用 AST 关系逐步升级到 LSP 或编译器级定义、引用、类型和实现关系，并补充 HTTP、RPC、消息和数据对象关系。

**版本化 Wiki**

借鉴 Qoder Repo Wiki 的预编译上下文思路，但增加 commit 绑定、来源哈希、审核状态和自动失效机制。

**受控混合检索**

根据任务选择文档语义、代码关键词、符号图和 Wiki，而不是固定执行所有检索，也不是让 Agent 无限探索。

**证据优先输出**

每个结论都应该能回到需求、代码、测试或 Wiki 来源。证据不足时返回缺口，而不是由模型补齐事实。

**多 Agent 接入**

平台只提供上下文和工具，不承担代码编辑。通过 MCP 服务不同 Agent，降低客户端和模型锁定。

## 4. 预期优势

### 4.1 相对代码上下文平台

不仅能找到相关代码，还能解释代码属于哪个需求版本、影响哪些测试，以及结论依据是什么。

### 4.2 相对企业知识搜索

不追求连接器数量，而是在少量研发数据源上提供 commit、symbol、test case 和 feature 级关系。

### 4.3 相对编码执行 Agent

不竞争执行能力，而是让不同 Agent 使用同一套经过版本约束和证据校验的内部上下文。

### 4.4 相对普通 RAG

普通 RAG 主要回答“哪些文本相似”。规划中的平台还要回答：

- 这些内容是否属于同一版本；
- 代码之间是否存在确定关系；
- 哪些关系只是推测；
- 测试是否真实执行；
- Wiki 是否经过审核；
- 当前信息是否足以支持结论。

### 4.5 最终选型

| 能力 | 决策 |
|---|---|
| 大规模通用代码搜索 | 需要时采购 Sourcegraph 类产品，不重复建设完整搜索平台 |
| 企业全域知识搜索 | 需要时采购 Rovo/Glean 类产品，不自建大量 SaaS connector |
| 代码生成与执行 | 使用 Copilot、Qoder、Cursor、Claude Code 等成熟 Agent |
| 内部研发版本和证据关系 | 自建并长期控制 |
| Agent 接入协议 | 使用 MCP，保持客户端可替换 |

最终原则：

> **让成熟产品负责代码搜索广度、企业连接广度和任务执行；我们负责正确版本、内部关系和证据可信度。**
