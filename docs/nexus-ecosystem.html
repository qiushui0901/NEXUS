nexuspow

组内共享的知识大脑，
本机顺手的开发双手

NEXUS 把需求、代码与测试沉淀成可回查的版本化知识，并通过 MCP 供给 IDE。 nexuspow 在本地搭好 Agent 工作区与研发流程。两者分工协作，而不是两套重复百科。

看清分工 协作链路 提效场景

01 · Products

两个产品，一件事

一件事是：让全组在写代码时，能快速、一致地拿到「这版需求怎么说、代码在哪、改了会影响谁」—— 并且结论带得走证据编号，而不是模型空话。

Shared service

NEXUS

部署在组内服务器上的版本化知识服务。 索引需求与代码，生成可审核的 Wiki，对外提供 REST / SSE / MCP。

  • 需求 RAG：按 document + version 隔离检索
  • 代码智能：多语言索引、调用图、影响分析
  • 版本 Wiki：确定性渲染，草稿须人审后发布
  • MCP：Cursor / Codex 只读调用组内真相
Local CLI

nexuspow

开发者本机的 Agent 工作区脚手架。 一键生成记忆文件、流程 skills，并可 clone 业务仓开始干活。

  • 初始化 AGENTS.md / MEMORY.md / docs/
  • 内置 brainstorm → plan → implement → test 流程
  • 本地可写仓库：编辑、编译、提交
  • 通过 MCP 连接共享 NEXUS，先证据后动手

02 · Architecture

代码两份副本，职责不混

GitLab 是真源。开发在本机改；NEXUS 在服务端建索引供查询。 MCP 不写你的仓库，只回答「在哪、影响谁」。 

GitLab（真源）
   │
   ├──► 本机 nexuspow 工作区     ← 写代码 / commit / push
   │         │
   │         │ MCP（只读）
   │         ▼
   └──► NEXUS 服务器            ← 索引 / Wiki / 检索 / 影响分析
              │
              ├── 需求证据  requirement:*
              ├── 代码证据  code:*
              └── 版本 Wiki / 冲突检测 / 草稿审核

03 · Knowledge layers

需求 RAG · 代码 RAG · Wiki

三者不是重复百科：前两者是探针与原始证据，Wiki 是审过的定稿目录。

层 原料 擅长 权威性
需求 RAG 文档分块 + 向量 这版需求怎么说 原始证据
代码 RAG 源码索引 + 符号图 代码在哪、谁调用谁 原始证据
Wiki 结构化事实页 功能在本版的全貌 派生视图（不能压过前两者）

Wiki 不用大模型生成正文：确定性从源 JSON 渲染。 LLM 用在开发方案、存疑、检索重排等处；正式 Wiki 须人审后发布。

04 · Why faster

效率从哪来

不是多一个聊天机器人，而是少找人、少翻文档、少漏影响、少串版本。

01

搞清需求

Agent 调 nexus_search_requirements / wiki_page，proposal 带 requirement:*。省掉翻飞书和对错版本。

02

动手之前

implement 前 impact_analysis：确定 / 推测 / UNRESOLVED 写进文档，再在本机改代码。

03

全组同口径

共享一台 NEXUS，同一 projectId + version；新人不必自建 Qdrant 全家桶。

04

流程不靠自觉

nexuspow skills 固定「先证据、后编码」，减少 Agent 跳步瞎改。
