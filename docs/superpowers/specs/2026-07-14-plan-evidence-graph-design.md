# 开发方案证据绑定与链路图设计

## 目标

重构开发方案页的信息组织方式，让每个开发环节都明确回答三个问题：它服务哪条产品规则、为什么要看这些代码、建议如何修改。同时修复源码查看跳转知识图谱、流式环节始终显示代码未命中和页面字号不一致的问题。

## 核心原则

- 产品规则、代码证据和建议改动必须绑定到具体开发环节，不再作为无法定位来源的全局列表。
- 真实代码节点只能来自 Qdrant 检索结果，不能由模型编造。
- 规划节点可以由模型生成，但必须使用虚线和独立样式与现有代码区分。
- 查看源码是覆盖在当前页面上的操作，不能改变用户所在的工作区。
- 空状态必须准确：只有整个代码检索确实为空时才显示未命中；环节匹配较弱时显示“推荐参考”及相关原因。

## 根因

1. `monitor.html` 的 `loadSource()` 在打开源码后强制把 `intentTab` 和 `activeTab` 改为 `graph`，因此开发方案页点击源码会跳到知识图谱。
2. 流式 `section` 事件协议只包含标题、用途、假设和建议，没有 `inspectTargets`。真实代码只在最后的 `references` 事件一次性返回，因此所有环节的“先看这些代码”始终为空。
3. 产品规则和代码引用被分别放在页面顶部和右侧，缺少与具体环节的关联字段。
4. 开发方案区域混用了全局标题、继承字号和局部 12px/13px 规则，导致相邻卡片字号不统一。

## 数据流设计

### 流式事件

模型继续逐行输出 NDJSON。`section` 事件新增以下字段：

```json
{
  "type": "section",
  "payload": {
    "title": "配置表设计",
    "purpose": "定义成长基金档位结构和领取校验所需配置",
    "relatedRules": [
      "档位按等级展示",
      "达到等级且已激活后才能领取"
    ],
    "keyQuestions": [],
    "changeSuggestions": [],
    "plannedNodes": [
      {
        "id": "planned-config-growth-fund-stage",
        "label": "ConfigGrowthFundStage",
        "type": "config",
        "description": "新增成长基金档位配置"
      }
    ]
  }
}
```

`relatedRules` 和 `plannedNodes` 可以由模型生成，因为它们属于需求解释和规划内容。`inspectTargets` 不允许模型生成。

### 真实代码匹配

服务端在收到每个 `section` 事件后，使用该环节的标题、用途、产品规则、假设和建议组成检索文本，在本次已从 Qdrant 返回的 `CodeChunk` 集合中计算相关度：

1. 类名、方法名和文件路径命中权重最高。
2. 代码正文关键词命中权重次之。
3. 入口、配置、状态、购买、领取、奖励、红点等业务类别提供同义词扩展。
4. 返回最多四个真实代码点，并为每个代码点生成 `relation`，解释它与当前环节的关系。
5. 若没有强匹配但本次存在代码结果，返回最接近的最多两个代码点并标记为 `recommended`，页面显示“推荐参考”，不显示“未命中”。
6. 只有本次代码检索结果整体为空时，才显示“未检索到代码，请检查代码索引或调整业务名称”。

增强后的事件由服务端流向页面：

```json
{
  "inspectTargets": [
    {
      "id": "...",
      "symbolName": "getConfigHeroGrowUp",
      "filePath": "...",
      "startLine": 120,
      "endLine": 160,
      "relation": "可参考静态表加载与按等级查询方式",
      "matchType": "exact"
    }
  ]
}
```

## 页面信息架构

页面主体保留两列，但右侧只保留实施顺序和风险。删除右侧孤立的“相关代码点”和“相关规则片段”。

```text
┌──────────────────────────────┬──────────────┐
│ 完整链路图                    │ 推荐实施顺序 │
│ 现有代码 ── 调用关系          │ 风险提醒     │
│       ╲                      │              │
│        ┄┄ 规划节点            │              │
├──────────────────────────────┤              │
│ 01 配置表设计                 │              │
│ 目的                          │              │
│ 关联规则                      │              │
│ 相关代码 + 相关原因 + 查看源码 │              │
│ 实现假设 / 建议改动           │              │
└──────────────────────────────┴──────────────┘
```

每个环节卡片内部顺序固定：

1. 标题和目的。
2. 关联产品规则。
3. 相关真实代码及相关原因。
4. 实现假设与约束。
5. 建议改动。

顶部“产品规则理解”和“开发约束与影响”改为紧凑概览，可用于快速浏览；具体环节仍重复显示真正相关的规则，因为该重复承担定位作用。

## 完整链路图

完整链路图展示两类节点：

- 现有节点：来自 Qdrant 代码图谱，按类、方法和文件类型着色；节点间真实关系使用实线。
- 规划节点：来自各环节的 `plannedNodes`；使用低饱和青色描边和虚线边，与现有节点明显区分。

规划节点通过对应环节的 `inspectTargets` 连接到现有代码。规划关系标签使用“扩展”“新增入口”“复用”“补充状态”等短语。点击现有节点打开源码；点击规划节点滚动并高亮对应开发环节。

图谱提供拖动、滚轮缩放、适配和全屏。初始状态自动适配并保留 12% 到 18% 留白，不产生页面级横向滚动。

## 源码查看

`loadSource()` 只负责请求 `/api/code/source` 并打开底部抽屉，不再改变 `activeTab` 或 `intentTab`。源码抽屉继续使用 Teleport 覆盖当前页面，支持底部模式、全屏和关闭。请求失败时保留当前页面，并显示明确错误提示。

## 字体与尺寸

开发方案区域使用独立但统一的字号体系：

- 页面标题：16px / 700。
- 环节标题：13px / 750。
- 正文、规则、建议和代码名称：12px / 1.55。
- 文件路径、关系原因和辅助标签：10px / 1.45。
- 图谱节点名称：10px；节点说明：9px。

所有卡片正文从同一个 CSS 变量继承，避免 `strong`、`li` 和 `.step` 各自继承出不同字号。

## 错误与空状态

- 代码检索整体为空：显示“未检索到代码，请检查代码索引或调整业务名称”。
- 环节没有强匹配但存在代码结果：显示“推荐参考”，并解释相关原因。
- 源码文件读取失败：源码抽屉不打开，当前页面不跳转，显示读取失败原因。
- 图谱接口失败：文字链路和环节内容仍可使用，图谱区域显示重试按钮。
- 流式生成中断：保留已收到的环节与代码映射，状态灯保持红色。

## 测试与验收

### 自动化测试

- 页面测试验证 `loadSource()` 不再修改工作区。
- 页面测试验证开发方案包含链路图、关联规则和代码相关原因。
- 服务测试验证流式 `section` 事件被真实代码结果增强。
- 匹配器测试覆盖精确命中、同义词命中、弱匹配推荐和代码结果整体为空。
- 完整 Maven 测试必须通过。

### 浏览器验收

- 开发方案页面相邻卡片字号一致。
- 每个环节能看到关联规则和相关代码原因。
- 点击源码后仍停留在开发方案页面，底部源码抽屉打开。
- 完整链路图同时显示实线现有节点和虚线规划节点。
- 图谱初始完整可见，可缩放、适配和全屏。
- 有全局代码命中时，环节不再错误显示“未命中”。

## 范围边界

- 不改变 Qdrant 的代码索引结构。
- 不让模型生成真实文件路径或真实代码节点 ID。
- 不重构独立的代码理解工作台。
- 不把开发方案和代码理解重新合并成一个页面。
