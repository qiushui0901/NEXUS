# 需求语义图文档级抽取改进方案

**版本：** 0.9.4（设计稿）  
**状态：** 待实施  
**适用模块：** `requirement.graph`、需求文档解析与多源知识图谱接入层  
**原则：** 代码是当前实现事实基线；需求文档提供历史意图、业务说明与漂移检测依据，不能覆盖代码事实。

---

## 1. 背景与目标

当前需求语义图采用以下链路：

```text
源文件 → Tika/清洗 → Parent Chunk → 重叠 Window → LLM 局部抽取
      → 实体/关系累加归并 → 证据校验 → 图快照/检索
```

该链路解决了模型上下文受限、逐窗重试和局部证据回溯问题，但抽取单位是窗口而非完整逻辑文档。对于跨章节定义、需求编号引用、表格约束、前置条件与验收准则分散描述等典型需求文档场景，存在全局语义断裂风险。

本方案的目标不是取消窗口化，而是将其升级为：

```text
文档结构骨架 → 结构感知局部抽取 → 跨窗口候选对齐
→ 二次关系补全/验证 → 多片段证据包 → 可版本化发布
```

最终获得“**局部抽取有边界、全局语义可整合、证据可复核、版本可追溯**”的需求语义图。

---

## 2. 当前实现与已确认问题

### 2.1 当前实现边界

当前 `RequirementGraphWindowPlanner` 基于 `ChunkRecord.parentText()` 按字符长度规划窗口：

- 按 `maxInputChars` 截断；
- 优先在换行、句号、分号、感叹号处分界；
- 窗口使用固定字符重叠；
- 窗口携带文件名、父块、章节路径、标题、父块顺序、字符偏移及前序窗口 ID；
- `RequirementGraphBuildService` 独立调用模型抽取每个窗口；
- `BuildAccumulator` 通过规范名、上下文和别名做抽取后实体合并；
- 证据以当前窗口的连续文本引文定位。

这意味着系统已经具备局部事实抽取、断点恢复、失败重试和窗口级证据定位能力；但尚未形成可靠的文档级语义整合层。

### 2.2 缺陷分级

| 优先级 | 缺陷 | 影响 | 当前缓解 | 结论 |
|---|---|---|---|---|
| P0 | 跨窗口、跨父块实体与关系割裂 | 漏抽跨段关系，实体重复或误合并 | 别名与规范名归并 | 只能缓解实体重复，不能发现未共现关系 |
| P0 | 窗口边界切断逻辑需求 | 半截需求、表格行和编号规则缺失 | 固定重叠、句末回退 | 对长需求与结构化内容不足 |
| P1 | 证据仅限单窗口连续引文 | 跨段事实无法获得完整直接证据 | `INFERRED`/不可用降级 | 应升级为多片段证据包 |
| P1 | 上游块身份耦合、证据回查易陈旧 | 重分块/重灌后旧快照难恢复、证据丢失 | `sourceRevision` 防止错误恢复 | 缺少源版本和构建语义双重版本化 |
| P1 | 短窗口异常膨胀风险 | 模型调用、成本和预算异常放大 | 当前无最小长度或回退阈值 | 需优先加入保护 |
| P2 | 继承解析与清洗损失 | 表格、编号、目录、图文关系失真 | 保留 `sectionPath` 等块元数据 | 仍非原始文档结构模型 |
| P2 | 重叠区重复抽取与预算截断 | 重复实体/冲突、部分图快照 | 归并与预算控制 | 需可观测、可量化、可降级 |

### 2.3 应避免的错误结论

1. **窗口化不是错误。** 它仍是受限上下文、失败隔离、可重试和证据可追溯的必要机制。
2. **400 字重叠不必然导致成本失控。** 其风险需要结合窗口数量、异常短窗、重试率和实际 token 计量评估。
3. **跨窗口事实不必然只能标为推断。** 若当前窗口已有明确引用文字，可形成局部直接证据；缺少的是组合多证据形成完整事实的模型。
4. **分块变化不必然触发重建。** 只有影响块集合或 `filename/parentId/contentHash/sectionPath/parentOrder` 等快照身份字段的变化才会使当前源修订变化。

## 3. 设计原则

### 3.1 文档事实与代码事实分离

需求语义图中的每条声明均须声明事实性质：

| 来源 | 语义定位 | 能否覆盖代码事实 |
|---|---|---|
| 代码图谱 | 当前实现事实；绑定 `repositoryId + commitSha` | 不适用，作为实现基线 |
| 参数/数值表 | 配置事实；绑定环境、版本和生效范围 | 否 |
| 测试结果 | 运行观测；绑定执行批次 | 否 |
| 测试用例 | 验证意图 | 否 |
| 需求文档 | 历史意图、业务说明、漂移检测对象 | 否 |
| 存疑项 | 待确认风险 | 否，且不得作为已确认事实发布 |

需求图提取结果应通过 `BusinessConcept` / `factKey` 与代码、参数、测试对齐；冲突应形成 `DOCUMENT_DRIFT` 等漂移结论，而不是由需求文本直接改写代码事实。

### 3.2 先结构、后局部、再整合

1. 先建立完整文档的结构骨架和稳定锚点；
2. 在逻辑单元内执行有界局部抽取；
3. 对跨窗口候选进行检索、聚类与二次验证；
4. 使用多片段证据支持跨段关系；
5. 最终通过质量门禁决定可发布范围。

### 3.3 可恢复必须绑定构建语义

图快照的可恢复性不能只依赖源块哈希，必须同时版本化：

- 源文档版本和内容修订；
- 解析器、清洗器和分块策略版本；
- 窗口规划参数与规划器版本；
- 本体版本、提示词版本、模型版本；
- 实体归并、跨窗对齐和关系验证策略版本。

## 5. 数据模型改进

### 5.1 文档结构与稳定锚点

新增或扩展以下逻辑对象：

```text
DocumentStructureNode
- id
- documentId, requirementVersion
- nodeType: DOCUMENT | SECTION | REQUIREMENT | LIST | TABLE | TABLE_ROW | FIGURE
- numberPath: 例如 3.2.1、REQ-001
- title
- parentNodeId, order
- sourceAnchorId

SourceAnchor
- id
- documentId, documentRevision
- anchorType: RAW_CHAR_RANGE | PAGE_RANGE | TABLE_CELL | REQUIREMENT_NUMBER
- startOffset, endOffset
- pageStart, pageEnd
- tableId, rowIndex, columnIndex
- locatorTextHash
- originalTextSnapshot 或 immutableObjectRef
```

要求：`SourceAnchor` 必须绑定不可变文档版本或保存必要的证据副本；不能只以当前 Qdrant 块哈希作为唯一回查依据。

### 5.2 逻辑单元与窗口上下文

```text
LogicalUnit
- id, documentId, documentRevision
- unitType: SECTION | REQUIREMENT | TABLE | ACCEPTANCE_CRITERIA | GLOSSARY
- structureNodeIds
- sourceAnchorIds
- text
- previousUnitSummary
- referencedRequirementIds
- knownEntityHints

RequirementGraphWindow
- 保留原有窗口字段
- logicalUnitId
- structureContext
- predecessorSummary
- referencedEntityHints
- plannerVersion
```

窗口输入增加“最小必要全局上下文”，而不是将全文塞入模型：所属章节路径、当前编号、前置定义摘要、明确引用的需求编号以及相关术语候选。

### 5.3 多片段证据包

将单一 `EvidenceQuote` 升级为 `EvidenceBundle`：

```text
EvidenceBundle
- id
- supportMode: DIRECT | COMPOSITE_SUPPORTED | INFERRED | UNAVAILABLE
- items[]

EvidenceItem
- sourceAnchorId
- windowId（可为空）
- quote
- startOffset, endOffset
- role: SUBJECT_DEFINITION | OBJECT_DEFINITION | RELATION_ASSERTION | CONSTRAINT
- extractionMethod: LLM | RULE | HUMAN
```

约束：

- `DIRECT`：单一证据片段明确陈述完整事实；
- `COMPOSITE_SUPPORTED`：多片段共同支持事实，每一片段均可回查；
- `INFERRED`：由规则或模型推断，必须保存推断规则、候选路径和置信度；
- `UNAVAILABLE`：不允许被计入“证据充分的已发布事实”。

### 5.4 构建指纹

新增：

```text
BuildFingerprint
- sourceRevision
- documentParserVersion
- textPreprocessorVersion
- chunkingStrategyVersion
- windowPlannerVersion
- maxInputChars, overlapPolicy
- ontologyVersion
- promptVersion
- modelId / modelVersion
- entityResolutionVersion
- crossWindowIntegrationVersion
```

恢复快照时，`sourceRevision` 与 `BuildFingerprint` 必须同时匹配；否则返回明确的 `GRAPH_BUILD_FINGERPRINT_STALE`，不可混用旧窗口结果。

## 6. 分阶段实施方案

### Phase 0：基线观测与回归样本（先做）

**目标：** 用真实数据确认问题比例，避免盲目改造。

**工作项：**

1. 为每次构建采集：父块数、窗口数、平均/最小/最大窗口长度、重叠比例、模型调用数、重试数、失败数、token 估算、预算中止原因。
2. 统计抽取质量：实体重复率、别名合并率、冲突关系率、`UNAVAILABLE` 证据率、`INFERRED` 关系率、发布后不可回查证据率。
3. 建立人工金标集，覆盖：
   - 同窗口实体与关系；
   - 跨窗口引用；
   - 跨章节定义—使用；
   - 编号化需求；
   - 参数表、验收表、例外条款；
   - 模糊或互相冲突的需求文本。
4. 将测试样本按文档而非窗口切分，避免同一文档片段同时进入训练/调参集与评估集。

**验收：** 能输出按文档、章节、窗口大小和失败类型分组的质量看板；至少形成 50 条人工核验的跨段关系金标。

### Phase 1：窗口规划器安全与结构感知改造

**目标：** 消除短窗膨胀，尽量不在逻辑单元内部切断。

**工作项：**

1. 为 `RequirementGraphWindowPlanner` 增加：
   - `minWindowChars`；
   - `maxBackwardBoundarySearchChars`；
   - `maxWindowCountPerParent`；
   - `minProgressChars`；
   - 规划异常状态与可观测指标。
2. 分界符优先级改为：需求编号/标题边界 > 表格行边界 > 列表项边界 > 段落 > 句子 > 强制字符截断。
3. 将固定字符重叠替换为可配置策略：
   - 结构单元不跨切时为 0；
   - 跨切时带前文摘要、需求编号和术语锚点；
   - 仅在无法形成摘要时使用有限文本重叠。
4. 保留原始偏移，确保窗口变更后证据仍能映射到 `SourceAnchor`。

**验收：**

- 任一父块不产生小于 `minWindowChars` 的非尾部窗口；
- 任一窗口推进距离不小于 `minProgressChars`；
- 同样语料下，窗口数不高于原实现的 110%；
- 长表格和编号需求的边界切断率显著下降。

### Phase 2：文档结构骨架与逻辑单元

**目标：** 给局部抽取提供可靠的全局结构上下文。

**工作项：**

1. 在 Tika 文本之外接入文档结构解析：标题层级、编号、列表、表格及页码；解析失败时降级为文本结构推断，并记录来源质量。
2. 构建 `DocumentStructureNode` 和 `SourceAnchor`；对需求编号建立稳定索引。
3. 基于结构树生成 `LogicalUnit`：一个逻辑需求、验收条件集合、表格或术语条目尽量不被拆散。
4. 预抽取文档级术语表、需求编号索引和显式引用边，作为后续窗口输入提示。

**验收：**

- 可由任一需求实体反查到文档章节、需求编号和原始位置；
- 编号引用解析 precision ≥ 95%（以金标集评估）；
- 不因新增结构层破坏现有纯文本、PDF 和 Office 文档降级路径。

### Phase 3：跨窗口实体对齐与关系补全

**目标：** 将“局部候选”升级为“可验证的文档级事实”。

**工作项：**

1. 将实体归并拆为两段：
   - 候选召回：规范名、别名、编号、术语表、向量相似度、章节邻近性；
   - 候选裁决：规则校验 + LLM 小上下文验证 + 人工确认入口。
2. 不再仅以 `type|canonical|context` 作为唯一实体键；为每个实体保留 `globalConceptCandidateId`、来源窗口、候选得分和裁决原因。
3. 从结构引用、实体共现、相同 `factKey`、关系缺口中生成跨窗口关系候选。
4. 对候选关系仅加载两端证据片段、结构路径和必要摘要，执行二次验证；禁止全文拼接。
5. 将“关系语义是否有效”与“关系两端是否同一实体”分开审计、分别评分。

**验收：**

- 跨窗口关系召回率较基线提升 ≥ 20 个百分点；
- 同名异义实体误合并率不高于基线；
- 每条跨窗口已发布关系均能说明候选来源、裁决过程与证据片段。

### Phase 4：多片段证据、版本治理和发布门禁

**目标：** 让图快照在源文档、分块和策略变化后仍然可解释、可安全失效。

**工作项：**

1. 落地 `EvidenceBundle`，支持跨窗口、跨父块证据片段组合。
2. 为每个图构建保存 `BuildFingerprint`；修改恢复、发布与重建规则。
3. 在证据回查时优先使用不可变原文锚点；当前向量库块仅作为检索加速索引，不能作为唯一证据真源。
4. 质量门禁按证据模式区分：
   - `DIRECT`、`COMPOSITE_SUPPORTED` 可进入受支持发布集；
   - `INFERRED` 只能作为候选或需要审核的关系；
   - `UNAVAILABLE` 不得用于“已证实”结论。
5. 文档、模型、提示词或本体版本变化时，明确标记快照为 `STALE`，并允许从可复用的逻辑单元结果做增量重建。

**验收：**

- 100% 已发布支持性声明拥有至少一个可回查锚点；
- 结构、模型或提示词变化不会静默复用旧抽取结果；
- 源文档更新后仍可展示旧快照对应的不可变证据，或明确说明证据不可用原因。

### Phase 5：接入多源对齐与人工治理

**目标：** 将需求文档定位为可与代码基线比较的意图来源。

**工作项：**

1. 将经证据门禁发布的 Requirement Claim 映射到 `BusinessConcept` / `factKey`。
2. 与代码图谱、参数表、测试用例和测试结果建立可审核的 `AlignmentRelation`。
3. 对不一致分别产生：
   - `DOCUMENT_DRIFT`：需求与当前代码实现不一致；
   - `CONFIG_DRIFT`：需求/代码默认与参数配置不一致；
   - `TEST_DRIFT`：测试意图或运行结果与代码/需求不一致。
4. 将存疑项作为开放风险接入：`OPEN Doubt → 受影响概念/代码/参数/测试 → 人工裁决 → Resolution Evidence → 重新计算漂移`。
5. 为审核关系补齐审核人、审核时间、理由、失效原因和重新发布记录。

**验收：**

- 需求文本永不覆盖已绑定 commit 的代码事实；
- 每项漂移可回溯到代码版本与需求证据；
- 人工确认、拒绝、过期和重审具备完整状态迁移记录。

## 7. API 与兼容性建议

### 7.1 兼容策略

保持既有构建接口可用，新增可选字段：

```json
{
  "documentId": "...",
  "requirementVersion": "...",
  "planningMode": "LEGACY_TEXT | STRUCTURE_AWARE",
  "crossWindowIntegration": true,
  "evidenceMode": "SINGLE_QUOTE | EVIDENCE_BUNDLE",
  "buildFingerprintPolicy": "STRICT"
}
```

初期默认使用 `LEGACY_TEXT + SINGLE_QUOTE`，通过项目级 Feature Flag 灰度启用结构感知模式。禁止将新旧模式的窗口结果混写到同一快照。

### 7.2 新增查询能力

1. 查询实体时返回：全局概念候选、所有来源窗口、结构路径、对齐状态。
2. 查询关系时返回：`EvidenceBundle`、证据模式、跨窗口裁决原因与置信度。
3. 查询快照时返回：`BuildFingerprint`、预算消耗、窗口异常和未完成原因。
4. 提供“文档结构浏览”和“跨窗关系待审核”接口，支持人工 Review。

## 8. 测试与质量评估

### 8.1 单元测试

- 边界选择：标题、编号、列表、表格、长句、无标点、Unicode 文本；
- 短窗保护：回退边界靠近开头时仍满足最小推进；
- 逻辑单元规划：需求编号与验收条件不被不必要拆分；
- `BuildFingerprint`：任一语义输入变化均禁止错误恢复；
- 多片段证据：偏移、锚点、缺片段和失效降级；
- 实体对齐：同义归并、同名异义隔离、编号精确匹配；
- 关系补全：候选生成不等于发布，必须经过验证和证据门禁。

### 8.2 集成测试

使用包含跨章节定义、参数表、测试用例及文档更新历史的真实脱敏样本，验证：

- 图构建、断点恢复、增量重建；
- 源文档更新或 Qdrant 重灌后的旧证据访问；
- 预算耗尽时结果范围和状态准确；
- 与 `BusinessConcept`、代码图谱和漂移结论的链路；
- 并发构建下快照、窗口和证据的一致性。

### 8.3 核心指标

| 指标 | 定义 | 建议目标 |
|---|---|---|
| 跨窗口关系召回率 | 金标跨窗关系中成功抽取并验证的比例 | Phase 3 后 ≥ 基线 +20pp |
| 跨窗口关系精确率 | 已发布跨窗关系中人工确认正确的比例 | ≥ 85% |
| 实体误合并率 | 不同实体被合并的比例 | 持续低于基线 |
| 实体重复率 | 同一金标实体形成多实体的比例 | 持续低于基线 |
| 证据可回查率 | 已发布支持性 Claim 可定位原文的比例 | 100% |
| 非支持发布率 | 无支持性证据而发布的 Claim 比例 | 0% |
| 窗口异常率 | 短窗、超额窗口、推进异常的比例 | < 0.5% |
| 预算截断率 | 因调用/时间/token 预算停止的构建比例 | 结合容量规划逐步降低 |
| 漂移人工采纳率 | 人工确认的漂移结论比例 | 用于调整对齐阈值 |

## 9. 风险与控制措施

| 风险 | 控制措施 |
|---|---|
| 增加结构解析后格式兼容性下降 | 保留纯文本降级路径，记录结构解析质量与失败原因 |
| 跨窗 LLM 二次验证成本上升 | 先规则/检索召回，严格限量候选；只发送两端证据和必要摘要 |
| 实体对齐误合并造成错误扩散 | 候选与裁决分离；低置信不自动合并；提供人工审核和可撤销关系 |
| 新旧快照语义混用 | 严格 `BuildFingerprint`；不同模式隔离存储 |
| 原文证据副本增加存储量 | 仅保存必要片段、压缩存储、保留对象引用与完整性哈希 |
| 文档不准确被误当实现事实 | 通过事实来源和 `DOCUMENT_DRIFT` 机制强制区分，代码版本始终为实现基线 |

---

## 10. 推荐交付顺序

1. **第一迭代：** Phase 0 + Phase 1。先提高稳定性与可观测性，避免在未知基线上做复杂整合。
2. **第二迭代：** Phase 2。完成结构骨架、逻辑单元和稳定原文锚点。
3. **第三迭代：** Phase 3 + Phase 4。实现跨窗关系补全、多片段证据和构建语义版本化。
4. **第四迭代：** Phase 5。接入代码事实基线、漂移治理和存疑闭环。

每个迭代均需在同一批真实文档金标集上与基线对比；若精确率降低或预算截断率上升，不进入下一阶段自动发布范围。

---

## 11. 完成定义（Definition of Done）

本方案完成的最低标准为：

- 窗口不再因边界回退产生异常短窗或近乎不前进的循环；
- 每个抽取窗口具备逻辑单元和结构上下文；
- 系统能够识别、验证并回查跨窗口关系；
- 已发布跨窗口关系采用可回查的多片段证据包；
- 快照恢复严格受源内容与构建语义双重版本约束；
- 需求图结果可与代码、参数、测试对齐并形成漂移，而不是覆盖代码事实；
- 建立可重复执行的金标评测与构建质量看板。

---

## 12. 结论

现有实现已经解决“如何以有限上下文、带证据地抽取局部需求事实”的问题；下一阶段应解决“如何把局部事实可靠地提升为文档级语义”的问题。

改造核心不是扩大模型上下文，也不是把所有资料粗暴混成一张图，而是：**让结构决定抽取边界，让候选对齐与二次验证补足跨窗语义，让多片段证据支撑全局事实，并始终以版本化代码事实为实现裁决基线。**
