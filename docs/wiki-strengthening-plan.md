# NEXUS Wiki 能力增强方案

> 基线版本：`0.8.3-SNAPSHOT`
>
> 目标：将当前 Wiki 从“结构化内容发布器”升级为“可持续更新、可审核、可追溯、能降低开发者和 Agent 探索成本的研发知识系统”。

## 1. 现状判断

当前 Wiki 的结构化契约、文件发布、缓存失效、草稿审核和回滚机制已经具备基础能力。真正薄弱的环节是内容生产。

当前主流程可以概括为：

```text
准备 VersionSource JSON
  -> 校验字段和页面关系
  -> 渲染 JSON / Markdown
  -> 原子替换发布目录
  -> 失效读取缓存
```

`WikiGenerationService` 的主要职责是校验、渲染和发布。它本身不会深入理解代码架构，也不会从仓库持续生成 Repo Wiki。

因此，当前系统更接近：

> **Wiki Publisher：将准备好的结构化内容安全发布。**

尚未成为：

> **Knowledge Compiler：从需求、代码、测试和历史版本中持续编译知识。**

## 2. 当前主要问题

### 2.1 页面生成过度依赖需求变化

当前知识构建主要读取当前和基线需求块，以需求变化生成候选功能页。

这种方式适合生成“版本需求变化摘要”，但不足以生成完整项目 Wiki。大量稳定知识不会因为本版本需求发生变化而进入页面，例如：

- 系统职责和边界；
- 技术栈和构建方式；
- 模块职责；
- API 和 RPC；
- 数据库、缓存和消息；
- 核心调用链；
- 配置项；
- 运行和故障处理方式。

### 2.2 Feature 识别规则过于粗糙

当前功能标题和 `featureId` 主要从需求文件名等信息派生，容易出现：

- 一个文件包含多个功能，却只生成一个页面；
- 同一功能分散在多个需求条目中，形成重复页面；
- 文件重命名后 feature ID 不稳定；
- 页面结构跟随文档组织，而不是业务领域组织；
- 历史版本中相同功能难以稳定匹配。

### 2.3 页面内容接近摘录拼装

当前产品规则主要是需求父块的有界摘录，代码内容主要是若干命中符号。测试建议也偏模板化。

这会导致页面存在以下问题：

- 能看到原文，但难以理解完整业务规则；
- 能看到相关符号，但缺少实现流程；
- 缺少模块、API、数据和配置关系；
- 无法区分主要入口、辅助实现和误召回候选；
- 测试建议没有建立在真实影响范围上；
- 页面之间缺少有意义的结构关系。

### 2.4 证据与正文关联不够细

当前页面可以包含证据列表，但证据主要集中展示在页面末尾。系统难以判断某条证据究竟支持正文中的哪项结论。

因此无法可靠计算：

- 哪些结论有需求证据；
- 哪些结论有代码证据；
- 哪些结论只来自模型概括；
- 某个源码位置失效后，影响页面中的哪些段落；
- 页面整体有证据，但关键结论是否仍无依据。

### 2.5 缺少持续增量更新

Wiki 版本可以重新生成，但目前尚未形成细粒度的页面失效传播：

```text
代码或需求变化
  -> 找到受影响符号或需求条目
  -> 找到受影响 Wiki 页面
  -> 标记页面过期
  -> 只重建这些页面
```

缺少这一机制会产生两个结果：

- 每次全量重建，成本高且审核量大；
- 不主动重建，Wiki 很快与源码和需求脱节。

### 2.6 缺少面向 Agent 的 Context 分层

当前主要提供完整 Wiki 页面。Agent 为了判断页面是否相关，可能需要先读取大量正文。

高效 Context 应至少分为：

- 项目级代码地图；
- 页面摘要；
- 标准 Wiki 页面；
- 可按证据下钻的详细事实包。

## 3. 目标定位

Wiki 不应只是自动生成 Markdown，而应承担三个职责。

### 3.1 人可阅读的研发知识

帮助开发、产品和测试理解：

- 系统如何组织；
- 某项功能为什么存在；
- 需求如何落到代码；
- 修改会影响什么；
- 哪些信息尚未确认。

### 3.2 Agent 可消费的预编译 Context

Agent 不需要每次重新扫描全部仓库。Wiki 应提供经过压缩的架构、模块、功能和版本上下文，再允许 Agent 按需下钻原始证据。

### 3.3 版本化的正式知识

Wiki 页面必须绑定需求版本、Git commit、测试快照和来源哈希。模型生成内容先进入草稿，经过审核后才能成为正式知识。

## 4. 目标信息架构

Wiki 建议分为稳定知识和版本知识两大部分。

```text
项目概览
├── 系统架构
├── 模块
│   ├── 模块 A
│   ├── 模块 B
│   └── 模块 C
├── API 与入口
├── 数据、缓存与消息
├── 功能
│   ├── 功能 A
│   └── 功能 B
├── 运行与配置
└── 版本
    ├── 版本 1
    └── 版本 2
```

### 4.1 项目概览页

内容：

- 项目职责和边界；
- 主要技术栈；
- 目录和模块；
- 应用入口；
- 外部服务；
- 核心数据流；
- 当前版本和知识健康状态。

主要来源：

- 构建文件；
- 应用配置；
- 目录结构；
- 代码入口；
- 路由和依赖；
- 版本清单。

### 4.2 模块页

内容：

- 模块职责；
- 对外接口；
- 主要类和函数；
- 上游和下游依赖；
- 读写的数据；
- 相关配置；
- 关联功能和测试。

### 4.3 功能页

内容：

- 功能摘要；
- 产品规则；
- 处理流程；
- 代码入口；
- 调用链；
- 数据与配置影响；
- 异常和边界；
- 验收标准；
- 真实测试状态；
- 版本变化；
- 风险与存疑；
- 声明级证据。

### 4.4 API 与入口页

内容：

- HTTP Route；
- RPC 方法；
- 消息消费者和生产者；
- 定时任务；
- CLI 或启动入口；
- 请求与响应模型；
- 调用实现；
- 关联需求和测试。

### 4.5 数据、缓存与消息页

内容：

- 数据库表或集合；
- 主要字段；
- 读写代码；
- 缓存 key 和失效规则；
- 消息 Topic 和事件；
- 数据生命周期；
- 相关配置和风险。

### 4.6 版本页

内容：

- 需求新增、修改和删除；
- 代码 commit 和变更文件；
- 受影响符号；
- 测试结果变化；
- Wiki 页面变化；
- 新增风险和未决问题；
- 与基线版本的兼容性说明。

## 5. 知识编译管线

建议将 Wiki 生成升级为独立知识编译流程。

```text
原始来源
  -> 确定性事实抽取
  -> 页面规划
  -> Evidence Bundle
  -> LLM 结构化综合
  -> 声明和证据校验
  -> Wiki 草稿
  -> 人工审核
  -> 正式发布
```

### 5.1 确定性事实抽取

先通过解析器、语言服务和现有索引抽取可以确定的事实，不让模型猜测。

#### 项目与构建事实

- 编程语言；
- 框架和版本；
- Maven、Gradle、npm 等依赖；
- 应用入口；
- 构建、测试和启动命令；
- 环境变量和配置文件。

#### 代码事实

- 类、接口、方法和函数；
- 定义、引用和实现关系；
- 调用边；
- HTTP、RPC 和消息入口；
- 数据库、缓存和消息访问；
- Git commit 和文件变化。

#### 需求事实

- 需求模块；
- 产品规则；
- 验收标准；
- 边界和异常；
- 当前版本和基线版本；
- 新增、修改和删除。

#### 测试事实

- 测试类和 case；
- CI 报告；
- 通过、失败和跳过状态；
- 覆盖模块和符号；
- 报告来源和执行时间。

### 5.2 页面规划

页面规划负责决定：

- 应生成哪些页面；
- 哪些需求条目属于同一个功能；
- 哪些已有页面应更新；
- 哪些页面应合并或拆分；
- 页面之间是什么关系。

页面规划输出结构化结果：

```json
{
  "pageId": "token-revocation",
  "pageType": "FEATURE",
  "title": "令牌撤销",
  "aliases": ["Token Revocation"],
  "requirementIds": ["req-31", "req-42"],
  "codeSymbols": ["AuthService.revoke", "RevocationCache.remove"],
  "relatedPages": ["token-validation", "session-management"]
}
```

规划结果必须允许人工调整，避免模型错误拆分或合并功能。

### 5.3 Evidence Bundle

每个页面生成前先构建专属证据包：

```json
{
  "pageId": "token-revocation",
  "requirementEvidence": [],
  "codeEntries": [],
  "callPaths": [],
  "apiRoutes": [],
  "dataObjects": [],
  "configuration": [],
  "testEvidence": [],
  "priorWiki": [],
  "versionChanges": []
}
```

Evidence Bundle 必须满足：

- 所有来源属于同一项目；
- 需求属于目标版本；
- 代码属于目标 commit；
- 源码位置可读取；
- 测试报告有真实来源；
- 历史 Wiki 明确标注版本；
- 每条证据有稳定 ID。

### 5.4 LLM 结构化综合

模型只根据 Evidence Bundle 组织页面内容，不负责创造事实。

模型输出使用严格 Schema：

- 页面摘要；
- 产品规则；
- 处理流程；
- 代码职责；
- 数据影响；
- 边界条件；
- 测试建议；
- 风险；
- 声明和证据 ID。

模型无法从证据中确认的字段应留空或进入知识缺口，不允许用常识补齐内部事实。

## 6. 声明级证据

每项重要结论应单独绑定证据，而不是只在页面末尾列出证据列表。

建议增加 `Claim`：

```json
{
  "claimId": "claim-17",
  "section": "process",
  "text": "撤销令牌后会清理本地缓存并发布失效事件",
  "support": "FULL",
  "evidenceIds": [
    "requirement:3",
    "code:7",
    "code-graph:2"
  ]
}
```

支持状态：

- `FULL`：证据直接支持完整结论；
- `PARTIAL`：证据只支持部分内容；
- `INFERRED`：根据结构关系推断，必须显式标记；
- `UNSUPPORTED`：没有有效证据；
- `CONFLICT`：多个来源互相冲突。

### 6.1 渲染方式

```markdown
撤销令牌后会清理本地缓存并发布失效事件。
[需求 3] [代码 7] [调用关系 2]
```

### 6.2 收益

- 精确统计声明覆盖率；
- 识别无证据段落；
- 点击结论跳转需求或源码；
- 源码变化后精确标记受影响声明；
- 审核人可以按结论确认或驳回；
- Agent 可以只读取与任务相关的声明和证据。

## 7. 增量失效与更新

每个页面记录构建清单：

```json
{
  "pageId": "token-revocation",
  "requirementHashes": [],
  "codeCommit": "...",
  "codeSymbols": [],
  "sourceHashes": {},
  "testSnapshotId": "...",
  "promptVersion": "wiki-v3",
  "generatedAt": "...",
  "reviewedAt": "..."
}
```

### 7.1 代码变化传播

```text
Git diff
  -> 变更文件和符号
  -> 调用图上游与下游
  -> 引用了这些符号的声明
  -> 受影响 Wiki 页面
  -> 标记 STALE
  -> 生成新草稿
```

### 7.2 需求变化传播

```text
需求父块变化
  -> 关联功能
  -> 声明和页面
  -> 标记 STALE
  -> 重新构建 Evidence Bundle
```

### 7.3 测试变化传播

```text
CI 测试结果变化
  -> test case
  -> 关联功能和符号
  -> 更新测试状态
  -> 页面重新审核
```

### 7.4 页面状态

建议保留清晰状态：

```text
DRAFT
PENDING_REVIEW
APPROVED
PUBLISHED
STALE
CONFLICT
REJECTED
```

正式页面发生来源变化时，只标记 `STALE` 并生成新草稿，不自动覆盖已发布内容。

## 8. 面向 Agent 的 Context 分层

借鉴 Repo Wiki 和 Repository Map，但增加版本与证据约束。

### 8.1 项目级 Repository Map

包含：

- 项目职责；
- 模块列表；
- 主要入口；
- 核心调用流；
- 外部依赖；
- 数据和消息；
- 当前版本变化；
- 已知知识缺口；
- 高频功能页。

### 8.2 页面三级内容

| 粒度 | 内容 | 使用场景 |
|---|---|---|
| 摘要 | 约 100 至 300 字、关键词、状态、来源版本 | Agent 快速判断相关性 |
| 标准页 | 完整业务和实现知识 | 开发者阅读、一般问答 |
| 证据包 | 原始需求、源码、调用边和测试结果 | 编码、影响分析和深度核验 |

### 8.3 MCP 读取方式

建议提供：

- 列出项目 Wiki；
- 获取 Repository Map；
- 按模块列出页面；
- 按 feature ID 读取摘要或标准页；
- 按 symbol 反查关联页面；
- 按证据 ID 下钻；
- 获取目标版本变化；
- 获取过期和冲突页面。

Agent 使用流程：

```text
读取 Repository Map
  -> 选择相关模块或功能
  -> 读取页面摘要
  -> 读取标准页
  -> 根据证据 ID 下钻需求、源码和测试
```

## 9. Wiki 质量门禁

当前证据数量不足以代表知识质量。建议增加以下指标。

### 9.1 覆盖指标

- 需求有功能页覆盖率；
- 模块有页面覆盖率；
- API 有页面覆盖率；
- 代码入口有功能关联率；
- 真实测试证据覆盖率；
- 关键声明证据覆盖率。

### 9.2 新鲜度指标

- `STALE` 页面比例；
- 页面对应 commit 与目标 commit 的差距；
- 失效源码引用数量；
- 过期需求来源数量；
- 等待审核时长。

### 9.3 一致性指标

- 跨项目证据数量；
- 跨版本证据数量；
- 冲突声明数量；
- 无证据声明数量；
- 重复或近似页面数量；
- 页面 relation 失效数量。

### 9.4 发布门禁

建议规则：

```text
跨项目证据 > 0                     -> 禁止发布
跨版本证据 > 0                     -> 禁止发布
无效源码引用 > 0                   -> 禁止发布
关键声明证据覆盖率 < 80%           -> 禁止发布
存在未处理 CONFLICT                -> 禁止发布
代码发生变化但页面仍 FULLY_VERIFIED -> 禁止发布
缺少真实测试快照                    -> 允许发布，但必须标记缺口
```

## 10. 分阶段实施

### P0：让 Wiki 内容成立

1. 增加项目概览、模块、API、数据和版本页面类型。
2. 从构建文件、代码索引和符号图抽取确定性事实。
3. 重做 feature 识别，不再主要依赖文件名。
4. 为每页构建 Evidence Bundle。
5. 使用 LLM 按严格 Schema 综合页面。
6. 增加声明级证据。

### P1：让 Wiki 不过期

1. 页面绑定需求 hash、commit、symbol、test snapshot 和 prompt version。
2. 根据 Git diff 和需求 diff 计算受影响页面。
3. 自动标记 `STALE`。
4. 只增量重建受影响页面。
5. 增加发布质量门禁。

### P2：让 Wiki 给 Agent 提效

1. 生成 Repository Map。
2. 页面提供摘要、标准页和证据包三种粒度。
3. MCP 支持按项目、模块、功能和符号读取 Wiki。
4. Agent 从 Wiki 声明下钻到需求、源码和测试。
5. 收集 Agent 实际读取、下钻和引用情况。
6. 根据使用数据合并、拆分或淘汰低价值页面。

## 11. 最小可行版本

第一版不需要完整复制 Qoder Repo Wiki 或 DeepWiki，也不需要引入新数据库。

MVP 范围：

```text
项目概览
+ 模块页
+ 功能页
+ Evidence Bundle
+ 声明级证据
+ commit/hash 失效
```

继续复用：

- 现有 JSON/Markdown 存储；
- 现有 Wiki Schema 的基础字段；
- 草稿审核状态机；
- 原子发布和回滚；
- WikiRepository 读取与缓存；
- 需求和代码证据 ID。

暂不实施：

- 新图数据库；
- 全公司通用知识搜索；
- 无限 Agent 自动写 Wiki；
- 自动发布模型生成内容；
- 一次性重写全部 Wiki 前端。

## 12. MVP 验收标准

- [ ] 能生成项目概览、至少一个模块页和功能页。
- [ ] 页面不是由文件名直接决定，功能可以合并多个需求条目。
- [ ] 每个功能页都有结构化 Evidence Bundle。
- [ ] 每条关键声明至少绑定一个证据，或明确标记为无证据。
- [ ] 页面可以从代码证据跳转到仓库相对路径和行号。
- [ ] Git commit 变化后，引用变更符号的页面自动标记 `STALE`。
- [ ] 需求内容哈希变化后，关联页面自动标记 `STALE`。
- [ ] 未审核草稿不能覆盖正式 Wiki。
- [ ] 跨项目、跨版本或失效证据会阻止发布。
- [ ] MCP 可以先读取项目 Map，再按页面和证据下钻。
- [ ] 已发布 Wiki 在模型和向量服务不可用时仍可读取。

## 13. 最终目标

最终 Wiki 构建方式应从：

```text
需求变化摘录
  -> 相关代码候选
  -> 拼装页面
```

升级为：

```text
需求 + 代码 + 调用关系 + API + 数据 + 测试 + 历史版本
  -> 确定性事实
  -> 页面规划
  -> Evidence Bundle
```
