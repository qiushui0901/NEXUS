# 代码知识库汇报

## 一、代码知识库结果汇总

目前已经具备需求、设计、开发、测试、数值和代码等多类研发资料，基本覆盖了从需求提出到开发验证的主要过程。

当前资料的主要问题是：

- 文档、代码和测试分散在不同位置；
- 查找信息比较依赖个人经验；
- 需求、设计、代码、测试和数值之间缺少关联；
- 版本变化后，历史规则不容易准确回查；
- 变更影响范围主要依赖人工判断，容易遗漏；
- 新人和跨团队成员需要频繁向熟悉业务的同事咨询。

因此，代码知识库的重点不应只是“搜索代码”，而是将研发资料串联起来，形成一条完整链路：

```text
需求
  -> 设计方案
  -> 开发方案
  -> 代码实现
  -> 测试用例
  -> 数值配置
  -> 版本变化
```

## 二、可以放入知识库的内容

### 1. 需求文档

- 需求背景、目标和业务规则；
- 功能流程、状态变化和边界条件；
- 需求编号、模块、负责人和版本；
- 验收标准和历史变更记录。

### 2. 设计方案

- 系统架构和模块职责；
- 关键流程、接口和数据关系；
- 设计约束、风险和兼容方案；
- 设计与需求、代码、测试之间的关联。

### 3. 开发方案

- 任务拆分和执行顺序；
- 需要修改的模块、文件和配置；
- 影响范围、测试要求和发布风险；
- 实际开发结果与原方案的差异。

### 4. 代码知识

- 仓库、项目、分支和版本；
- 文件、模块、类、方法和函数；
- 代码实现、调用关系和配置使用；
- 代码与需求、设计方案、测试用例的关联；
- 历史提交和版本差异。

### 5. 测试用例

- 测试目标、前置条件和操作步骤；
- 正常、异常和边界场景；
- 测试与需求、代码和数值的对应关系；
- 测试执行结果、失败原因和历史缺陷。

### 6. 数值表

- 概率、倍率、阈值、等级和区间；
- 参数的生效版本和调整记录；
- 数值与需求、代码、测试之间的关联；
- 数值变化后的影响范围。

## 三、知识库的方向

知识库建议定位为：

> **面向研发的需求、设计、开发、代码、测试和数值关联查询工具。**

重点不是做一个泛化问答机器人，而是帮助研发人员快速回答以下问题：

1. 这个需求具体要改什么？
2. 相关设计方案和代码在哪里？
3. 修改一个需求或数值会影响哪些代码和测试？
4. 某个历史版本当时的规则是什么？
5. 需求、代码、测试和数值之间是否存在缺失或冲突？

建议优先建设四个方向：

### 1. 需求追踪

输入一条需求，关联对应的设计方案、开发方案、代码、测试和数值。

### 2. 变更影响分析

输入需求变更、代码提交或数值调整，输出受影响的模块、测试和风险。

### 3. 版本回查

查询指定版本的需求规则、设计结论、代码实现和测试结果，避免使用错误版本的信息。

### 4. 发布前检查

检查需求是否有实现、实现是否有测试、数值是否一致、相关文档是否需要更新。

## 四、方案细节

### 1. 查询方式

用户可以用自然语言进行查询，例如：

```text
验证码失败后多久可以重试？
这个规则在哪些模块实现？
和这个需求相关的测试有哪些？
5.0 和 5.1 版本的数值有什么变化？
```

系统返回相关的需求、设计、开发、代码、测试和数值内容，并显示来源和版本。

### 2. 结果组织

结果不只返回一段相似文本，而是尽量按照以下方式汇总：

```text
需求内容
设计依据
开发影响
代码位置
测试覆盖
数值配置
版本变化
发现的问题
```

### 3. 重点原则

- RAG 用于快速找到相关内容；
- 需求编号、版本、测试编号和数值需要明确关联；
- 数值问题需要支持精确查询，不能只依赖相似度；
- 重要结论必须能够回到原始文档、代码或测试；
- 对无法确认的内容明确标记，不能把推测当成事实。

### 4. 第一阶段建议

第一阶段不建议覆盖所有研发场景，先验证一个完整闭环：

> **输入一条需求，输出相关设计、开发、代码、测试、数值，以及缺失和冲突项。**

这个场景同时涉及多种资料，也最容易体现知识库是否减少了查找时间和遗漏。

## 五、验证方式

### 1. 对照实验

选择 20～30 个真实研发问题，对比两种方式：

- 传统方式：查文档、搜代码、问同事；
- 使用知识库：在原有工作方式上增加知识库辅助。

同一批人员交叉使用两种方式，减少个人能力差异带来的影响。

### 2. 重点观察指标

- 完成需求分析所需时间；
- 找到正确代码和测试的时间；
- 需求、代码、测试或数值的遗漏数量；
- 历史版本引用错误次数；
- 后续返工次数；
- 向老员工求助的次数；
- 使用者是否愿意继续使用。

### 3. 初步判断标准

- 任务完成时间降低 25% 以上；
- 正确率不低于原有方式；
- 影响分析遗漏降低 30% 以上；
- 版本和数值类问题没有明显错误；
- 使用者认可它确实减少了查找和整理工作。

只证明检索 Recall、访问量或调用次数提升，不能说明研发真正提效。最终需要证明任务完成得更快、更完整，并且返工更少。

## 六、阶段性结论

代码知识库的价值不只是“让 AI 更懂代码”，而是把分散的研发资料串起来，帮助团队解决：

- 信息找不全；
- 历史版本查不准；
- 变更影响评估不完整；
- 需求、代码、测试和数值之间断链；
- 新人过度依赖老员工；
- 发布前难以及时发现缺口。

下一步建议先用真实需求做小范围对照实验。先证明它能减少分析时间和遗漏，再决定是否继续扩大知识库范围。
