02 / 09
01 · MARKET SEGMENTATION

市场上不是一种产品，
而是四条技术路线

代码上下文平台 Sourcegraph

关键词搜索、代码图、跨仓上下文，为 LLM 找到相关代码。

相对缺口：需求版本、测试快照和 Wiki 发布不是核心数据模型。

企业知识搜索 Rovo · Glean

连接 Jira、Confluence、Drive、Slack 等 SaaS，把组织知识送入搜索和 Agent。

相对缺口：连接广但研发语义浅，commit 级符号关系和版本证据不是核心。

编码执行 Agent Copilot · Gemini · Q · Devin

理解当前任务，修改代码、运行测试、评审 PR 或操作云资源。

相对缺口：擅长“完成任务”，但不负责长期维护内部需求事实与证据生命周期。

研发证据基础设施 NEXUS

把需求版本、代码 commit、测试快照、Wiki 和证据 ID 建成可追溯的数据契约。

我们的取舍：不再造 IDE，不追求连接所有 SaaS；聚焦研发事实深度，并通过 MCP 服务现有 Agent。

结论：真正的替代关系只存在于局部能力；整体上 NEXUS 更接近“大厂产品之间缺失的证据层”。

03 / 09
02 · CODE INTELLIGENCE

Sourcegraph 更强在代码规模，
我们更深在版本证据

Sourcegraph CodySEARCH-FIRST
怎么做

Keyword Search + Sourcegraph Search API + Code Graph，为聊天和生成拉取跨仓代码上下文。

优势

大规模代码搜索、成熟索引、跨代码托管平台、IDE 体验和多仓上下文明显更成熟。

局限

核心对象是 repo/file/symbol；需求版本、测试执行快照、Wiki 审核发布需要外部系统承载。

结果

很擅长回答“代码在哪里、怎么用”，但“某需求版本为何这样实现、测试是否跟上”不是原生闭环。

我们的规划EVIDENCE-FIRST
准备建设

混合代码检索、编译器/LSP 语义索引、commit 级关系快照，以及 HTTP、RPC、消息和数据对象关系。

输出方式

每条代码证据携带仓库、commit、文件、符号、行号和关系置信度。

主动取舍

不复制完整通用代码搜索，把投入集中在需求版本与代码、测试的关联上。

预期优势

从“找到相关代码”升级为“需求版本 → 代码证据 → 影响范围 → 回归建议”。

技术判断：若目标只是企业代码搜索，优先采购 Sourcegraph；若目标是需求到代码和测试的版本化追溯，单独采购仍需建设证据层。
04 / 09
03 · ENTERPRISE KNOWLEDGE

Rovo / Glean 赢在连接广，
我们赢在研发语义深

Rovo / GleanCONNECTOR-FIRST
怎么做

通过大量 SaaS connector 和组织知识图谱，把人员、项目、文档、会议与工作项统一搜索。

优势

冷启动快、数据源覆盖广、组织级搜索和工作流自动化成熟，尤其适合 Jira/Confluence 体系。

局限

通用连接器通常保留文档级语义，不会为每个仓库建立 commit 隔离的调用图和解析置信度。

约束

Rovo 完整 AI 能力依赖 Atlassian Cloud 计划；跨系统事实版本如何冻结由各数据源决定。

我们的规划DOMAIN-FIRST
准备建设

统一项目、需求版本、代码 commit、测试 case 和 Wiki feature 的研发对象模型。

接入范围

优先需求平台、Git、CI 测试和版本 Wiki，不建设全公司通用 connector 市场。

版本策略

保留原始来源和历史快照，不只索引各系统的当前状态。

预期优势

用更窄的数据源范围换取 commit、test case 和 feature 级的研发深度。

技术判断：企业全域搜索应采购 Rovo/Glean；研发关键事实不能只停留在 connector 抽取结果，需要独立的版本和证据契约。

04 · CODING AGENTS

Copilot 与 Qoder
两种 Agent 上下文路线

Copilot / QoderEXECUTION-FIRST
Copilot

以 GitHub、IDE、CLI、Issue、PR 和 MCP 为上下文与工具入口，优势是从任务直接进入代码和 PR 交付。

Qoder

强调 Context Engineering、Repo Wiki、规则与记忆，并通过目标循环和多 Agent 支撑长任务。

共同优势

编辑器、终端、测试、PR 和多文件修改成熟；预编译 Context 能降低重复探索成本。

共同局限

当前会话上下文和 Repo Wiki 不天然等于已审核、可长期复现的业务版本事实。

我们的规划CONTEXT CONTROL
准备建设

通过 MCP 提供需求、代码、源码、调用图、影响分析、版本 Wiki、存疑和冲突工具。

Context

建设绑定 commit、来源哈希和审核状态的版本化 Repo Wiki，支持摘要后按证据下钻。

边界

不写代码、不操作 PR，把快速变化的执行能力留给 Copilot、Qoder 等成熟 Agent。

预期优势

不同 Agent 共用同一正确版本和证据协议，避免客户端锁定与上下文漂移。

技术判断：自建 Coding Agent 性价比低；自建 MCP 证据服务能利用所有 Agent，又不被单一客户端绑定。

05 · STORAGE DECISIONS

为什么不是“一个向量库解决一切”

OPTION A

全量塞进向量库

大多数轻量 RAG 的路径：文档和代码统一 chunk、embedding、topK。

  • 实现最快
  • 语义近似强
  • 关系与版本 diff 弱
  • 难表达“未解析”和置信度
不选：相似不等于调用关系，向量分数不能充当版本事实。
OPTION B

统一图数据库

把需求、代码、测试、人员和版本都建成大图，再做图检索。

  • 关系表达丰富
  • 跨域查询强
  • 建模、运维和增量一致性成本高
  • 当前规模收益不足
暂不选：没有需要分布式图查询的实际规模证据。
CHOSEN

Qdrant + SQLite + 文件事实

按数据语义分治，而不是按技术时髦程度统一。

  • Qdrant：dense/desc_dense/sparse 召回
  • SQLite：事务化 commit 调用图
  • JSON/Markdown：可审阅版本与 Wiki
  • 稳定 ID 在三者间关联
优势：最小运维成本下，同时保留语义、关系和可审阅事实。

代码索引采用版本化 collection + Alias 原子发布；需求索引先写入并校验，再清理旧 point，避免在线半成品。

06 · MODEL & ORCHESTRATION

为什么不押注一个模型，
也不做无限 Agent 循环

MONOLITHIC MODEL

单模型 + 大上下文

把代码和文档尽量塞进长上下文，依靠模型自行判断。

  • 原型简单
  • 成本和延迟随上下文上涨
  • 版本污染难诊断
  • 模型替换会改变全链路行为
不选：无法建立确定的质量门和证据边界。
OPEN-ENDED AGENT

自主规划与反复检索

让 Agent 自己选择工具，直到认为信息足够。

  • 灵活
  • 行为难复现
  • 工具调用和 token 不可控
  • 错误上下文可能被持续放大
不选：研发证据服务首先需要确定性和可运营性。
CHOSEN

任务路由 + 有界两跳

不同任务选择生成、评审、标注或重排模型；检索策略最多补检一次。

  • Spring AI + OpenAI Compatible 解耦供应商
  • 规则反思检查唯一父块和双侧覆盖
  • 失败显式 DEGRADED
  • 冻结质量集进入 CI
优势：模型可替换，成本有上限，失败原因可聚合。

我们的优势不是模型参数更大，而是模型之外仍有可测试的检索、版本和证据契约。

08 · FINAL DECISION

不是全面替代大厂，
而是控制最关键的一层

OUR ADVANTAGE

值得自建的部分

  • 内部语义：需求版本、代码 commit、测试与 Wiki 的关系由我们定义。
  • 证据契约：稳定 ID、引用白名单、冲突与降级不会随模型更换消失。
  • 供应商中立：模型按任务路由，Agent 通过 MCP 替换，业务事实留在内部。
  • 可审计发布：向量索引原子切换，Wiki 有审核和回滚，质量有固定 CI 门禁。
  • 组合差异：单项不与大厂硬拼，但需求到代码、测试和版本的闭环市场覆盖稀缺。
COST & BOUNDARY

必须承认的代价

  • 代码搜索规模和精度不及 Sourcegraph。
  • 企业连接器数量不及 Rovo/Glean。
  • 代码执行和 IDE 体验不及 Copilot/Devin。
  • 需要自行维护索引、评测和领域 loader。
  • 只有持续积累真实需求、代码和测试关联，差异化才成立。
最终选型：采购或使用成熟 Agent 负责“执行”，必要时采购通用搜索负责“广度”；NEXUS 只控制不可外包的内部研发事实、版本关系与证据质量。

一句话：他们优化“模型能做什么”，我们控制“模型依据什么做”。

07 · WIKI PRODUCTIVITY

Wiki 的价值不是文档更多，
而是探索更少

现有 Wiki / ContextPRECOMPUTE
Qoder

Repo Wiki 预先理解架构和设计，为长任务提供持久 Context。

DeepWiki

把代码仓库生成可浏览、可问答的 Wiki 和系统图，适合陌生项目理解。

Context Files

AGENTS.md、Rules、Repository Map 保存约定、命令和代码地图。

共同收益

我们的规划VERIFIED CONTEXT
分层

仓库架构、模块说明、功能 Wiki、符号证据，先摘要再下钻。

版本

每份 Context 绑定需求版本、Git commit 和来源哈希，代码变化后增量失效。

审核

模型只生成草稿，人审核后发布；与代码、需求或测试冲突时告警。

共享

通过 MCP Resource 和标准 Context 文件服务多个 Agent。

预期优势：从“自动生成 Wiki”升级为“可失效、可审核、可追溯的 Context”，既降低 Agent 探索成本，也避免旧摘要长期传播。
06 · EXPECTED ADVANTAGE

三类成熟产品负责能力，
我们负责上下文可信

01 · VS CODE CONTEXT

从相关代码到版本影响

不只返回“可能相关”的代码，还准备把需求版本、代码关系和测试范围串成可回查路径。

02 · VS ENTERPRISE SEARCH

从连接广度到研发深度

不竞争 connector 数量，重点提供 commit、symbol、test case 和 feature 级关系。

03 · VS CODING AGENT

从当前会话到长期事实

Agent 可以更换，但正确版本、正式 Wiki、测试来源和证据协议保持稳定。

04 · PLATFORM VALUE

执行与事实解耦

成熟产品持续升级模型和执行能力；内部平台长期控制不能外包的需求、版本和证据关系。

最终选型：需要代码搜索时使用 Sourcegraph 类平台，需要企业搜索时使用 Rovo 类平台，执行使用 Copilot/Qoder；内部只建设研发版本与证据层。
